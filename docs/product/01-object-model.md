# 01 — The object model

The nouns werk deals in, what each one means, and how they relate. Getting these
right is most of the product: if the model is clean the CLI, the TUI and the web
UI all fall out of it, and if it isn't, no amount of interface design rescues it.

```
Fleet
└── Placement            where work can happen        local · ssh:host · container
    └── Workspace        a named, isolated place      "affectionate-badgers-writing"
        ├── Checkout     files + branch (optional)    werk/affectionate-badgers-writing
        └── Session      a persistent terminal        claude · npm run dev · zsh
                                                      (one or more per workspace)

Project                  a repository, spanning       groups workspaces across
                         placements                   every placement
```

Two axes, deliberately crossed: a **placement** is a physical fact (which
machine), a **project** is a logical one (which codebase). A workspace sits at
the intersection. The fleet view can be pivoted either way, and it should be —
"show me everything on bigbox" and "show me everything for the api repo" are both
questions people ask.

---

## Workspace

**The central noun.** A named, isolated place where work happens.

`affectionate-badgers-writing`. Three words, human-pronounceable, generated by
default, overridable with `--name`. The name is the handle for everything: it
identifies the workspace in every UI, and it derives the branch name, the
container name, and the directory name.

A workspace has:

|                            |                                                                                     |
| -------------------------- | ----------------------------------------------------------------------------------- |
| **Name**                   | Unique across your fleet. Stable for the workspace's life.                          |
| **Placement**              | Where it physically lives. Fixed at creation (moving is a separate, later feature). |
| **Checkout**               | Its files, and — if it's a repo — its branch. Optional.                             |
| **Sessions**               | One or more persistent terminals. Created with at least one.                        |
| **Status**                 | Derived from its placement and its sessions. See below.                             |
| **Created / last-touched** | For sorting the list and for garbage collection.                                    |

The workspace is the **unit of isolation** and the **unit of cleanup**. Everything
werk made for you is reachable from the workspace and destroyed with it:
its branch, its container, its directory, its sessions, its recordings. There is
no orphan state that survives `werk rm` and no state you have to clean up by
hand somewhere else.

It is also the **unit of the promise "the work comes back"**. Destroying a
workspace that holds commits your local repository has never seen must be
something werk refuses to do quietly.

### Workspace status

| Status         | Meaning                                                                                                                           |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `provisioning` | Being created. Container starting, repo seeding, branch being cut.                                                                |
| `ready`        | Exists and is reachable; no session is doing anything interesting.                                                                |
| `running`      | At least one session has a live, active process.                                                                                  |
| `needs you`    | At least one session is asking for attention. **The status that matters.**                                                        |
| `stopped`      | Deliberately suspended. Container paused / host asleep. Resumable.                                                                |
| `unreachable`  | We can't get to it right now. Host down, network gone, docker not running. Distinct from stopped — this is a fault, not a choice. |
| `archived`     | Kept for its scrollback and its branch, but nothing is running.                                                                   |

`unreachable` deserves emphasis. Once werk spans machines, "I don't know" becomes
a routine state rather than an error, and the UI has to be honest about it
without being alarming. A workspace on a laptop that's closed is not broken.

## Placement

**Where a workspace physically lives.** The concept that makes "run this
somewhere" a parameter instead of an architecture.

| Kind                           | What it means                                                                              | Provisioned by werk?                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| `local`                        | Your machine.                                                                              | n/a                                                                    |
| `ssh:<host>`                   | An existing machine you have ssh access to.                                                | No — you already have it.                                              |
| `container:<host>`             | A container werk creates and owns, on a docker host that is itself either local or remote. | **Yes.** Created, named, kept alive, and destroyed with the workspace. |
| _(later)_ `sandbox:<provider>` | A cloud sandbox — E2B, Fly Machines, Modal, Coder, and friends.                            | Yes.                                                                   |

The distinction that matters for the product is **who owns the lifecycle**. A
`ssh:` placement is borrowed — werk puts a directory and a daemon on it and is a
polite guest. A `container:` placement is owned — werk made it, werk is
responsible for keeping it alive, and werk destroys it. Users will reason about
these differently and should be shown them differently.

Placement is where the fifth promise gets paid: **werk installs itself.** On
first use of any `ssh:` or `container:` placement, werk gets its own binary onto
that machine, starts a daemon, and from then on the remote machine is just
another source of rows in your list. You never `apt install werk` on a box.

**Placement is a parameter, so it has a default**, per-project or globally. A
team that has agreed "agents run in containers on the build box" configures that
once. `werk create` with no flags should do the right thing for you nine times
out of ten.

### Placement status

Placements are reachable or not, and that is a first-class thing to display —
one unreachable host should show as _one_ row saying "bigbox: unreachable",
not as eleven workspaces each individually failing.

## Checkout

**A workspace's files, and how they got there.**

| Kind       | Meaning                                                                                                                     | Branch?               |
| ---------- | --------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| `worktree` | A `git worktree` of your local repo. Local placements only. Fast, shares the object store.                                  | Yes, werk creates it. |
| `clone`    | A fresh copy of the repository on the target machine. The normal case for remote and container placements.                  | Yes, werk creates it. |
| `in-place` | Just use this directory. No branch created, no isolation. The "I want a persistent terminal here, don't touch my git" case. | No.                   |
| `none`     | No repository at all. An empty or arbitrary directory. Free-floating.                                                       | No.                   |

**Git is optional and that is load-bearing.** `werk create` in a non-repo
directory, or `werk create --no-repo`, gives you a workspace with a `none`
checkout. A long-running `tail -f` on a server is a legitimate werk workspace and
should not feel like an abuse of the tool.

### What "the code gets there" means

For `clone` checkouts, seeding is werk's job, and it is a product surface, not
plumbing, because the user has expectations about it:

- It should be **fast**, and the speed should be visible (`1.2 GiB seeded in
3.4s`) because seeding is the one part of `werk create` with a noticeable
  duration.
- It should carry **the branch you're on**, not just `main`.
- It should have a defensible answer for **uncommitted work**. Carrying your
  dirty working tree by default is what people expect and what makes the tool
  feel magical; it's also a footgun if it silently commits things. This is an
  open question — see [04-open-questions.md](04-open-questions.md).
- It should have a defensible answer for **ignored-but-necessary files** —
  `.env`, credentials, local config. An agent in a container that can't run the
  app because there's no `.env` is a workspace that wasted your time.

### What "the work comes back" means

The reverse direction, and the more important one. The user must be able to get
commits made in a workspace into their local repository, and the tool must make
that easy enough that they actually do it. Whether that's an explicit `werk
pull <name>`, an automatic push-on-commit, or a background sync is an open
question — but the _guarantee_ is not: **werk does not destroy unreturned work.**

## Session

**A persistent, detachable terminal holding one process tree.**

The layer [`../research/`](../research/) covers exhaustively: the daemon holds
the PTY master, the terminal state is reconstructed faithfully on reattach,
detaching mid-escape-sequence is safe, and sessions survive the daemon
restarting.

What the workspace layer adds on top of it:

- **A workspace can hold several sessions.** Your agent in one, a dev server in
  another, a log tail in a third. `werk create` makes one; `werk run` adds more.
  This is not panes — they are separate terminals you attach to separately — but
  it means "what is this workspace doing" is a plural question.
- **Sessions are attachable from anywhere.** From the CLI on the machine they run
  on, from the CLI on your laptop (over ssh), or from the browser. Multiple
  simultaneous attachments, with at most one writable by default and the rest
  read-only — "watch what the agent is doing" is a core use case.

### Session status

| Status      | Meaning                                                                                                                                                     |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `running`   | The process is doing something. Output recently.                                                                                                            |
| `idle`      | Alive, but quiet.                                                                                                                                           |
| `needs you` | Asking for attention. See below.                                                                                                                            |
| `exited`    | The process finished. Exit code retained. Scrollback retained.                                                                                              |
| `lost`      | The daemon has the screen but not the process — e.g. restored from a snapshot after a host reboot. Read-only corpse. Useful, but must be labelled honestly. |

## Attention

**The derived signal that the whole fleet view exists to surface.** Not really a
noun — a property of a session that gets promoted up through the workspace to the
list.

A session needs you when it:

- rang the **bell**,
- emitted a **desktop notification** (OSC 9 / OSC 777),
- reported **progress complete** or **progress error** (OSC 9;4),
- **exited**, especially non-zero,
- has been **idle after being busy**, which for an agent almost always means it
  asked a question and is waiting.

The first four are structured signals any well-behaved program emits, and werk
gets them for free from the terminal emulator layer. The fifth is a heuristic and
must be labelled as one.

Building attention on emitted signals rather than on the rendered screen is what
makes it work for every agent and every process without a werk release per
vendor — the sixth promise in [00](00-what-werk-is.md). agentapi's documented
fragility is the cautionary tale in the other direction: it diffs rendered text,
and every Claude Code UI change breaks it.

Attention has a **read state**. Once you've looked at a session, it stops
shouting. This is the difference between a useful list and a list of eleven
permanently-highlighted rows that you learn to ignore.

## Project

**A repository, as a grouping key across placements.**

Not a thing werk creates — a thing werk recognises. Its whole job is to make the
fleet list group sensibly:

```
werk    affectionate-badgers-writing    docker:local   ● running
werk    sleepy-otters-counting          ssh:bigbox     ◆ needs you
api     brave-herons-planning           local          ○ idle
```

The interesting question is **identity**: how does werk know that the checkout on
your laptop, the clone in a container, and the worktree on bigbox are all "the
werk repo"? Remote URL is the obvious key and is wrong in several ways (ssh vs
https forms of the same repo, forks, repos with no remote at all). The root
commit hash is stabler. This is a real decision — see
[`../research/10-git-workspaces.md`](../research/10-git-workspaces.md).

Projects also carry **configuration**: the default placement for this repo, the
default command, the branch prefix, what to copy that git ignores. A checked-in
`werk.toml` (or similar) that says "agents for this repo run in a container from
this image" is a strong feature and cheap to add — but it is configuration
werk _reads_, not a thing werk manages.

## Fleet

**Every workspace on every placement, as one collection.**

The fleet is what `werk` with no arguments prints and what `werk serve` renders.
It is an aggregation, not a stored object — assembled from the local daemon plus
every remote daemon werk knows how to reach.

Two properties it must have:

1. **It degrades gracefully.** An unreachable placement means missing rows,
   clearly marked, not a failed command. The list must render usefully when half
   your machines are asleep.
2. **It is fast enough to run reflexively.** `werk` should feel like `ls`, not
   like a status page that takes four seconds to poll six ssh connections. This
   is a real constraint and it argues for caching plus background refresh rather
   than fan-out-on-demand.

The genuinely open question is **whose fleet it is**: is it "workspaces this
laptop created", or "workspaces you own, discoverable from any of your
machines"? The second is much better and much harder — it implies either
discovery on each known host or a piece of shared state somewhere. Flagged in
[04-open-questions.md](04-open-questions.md).

## Naming, and the mapping problem

One workspace name has to become a git branch, a container name, a directory
name, and a URL path, on three operating systems. Those have different legal
character sets and different length limits.

Generated names — `affectionate-badgers-writing` — sidestep almost all of this by
construction: lowercase ASCII words joined by hyphens are legal everywhere. But
`--name` lets the user pick, so the rules have to be stated and enforced at
creation rather than discovered at container-create time. The constraints worth
knowing (`git check-ref-format`, Docker's `[a-zA-Z0-9][a-zA-Z0-9_.-]*`, Windows
path length and reserved names) are catalogued in
[`../research/10-git-workspaces.md`](../research/10-git-workspaces.md).

Derived names should be **prefixed and obvious**: branch `werk/<name>`, container
`werk-<name>`, directory `<workspaces-root>/<name>`. Someone looking at
`docker ps` or `git branch` must be able to tell at a glance what made this and
that deleting it is safe once the workspace is gone.
