No. 1  ·  Late edition A paper about where software gets written now

The werk Dispatch

Coding agents are terminal programs. They run for forty minutes without you, and there is no reason at all for those forty minutes to happen on the machine in your bag.

The machine room  /  Comment

The laptop stopped being the place

Work now outlives the session you started it in. werk starts a process somewhere and lets you come back to it later — on a machine you choose, on a fresh branch, with the terminal still open when you get back.

By our own correspondent  ·  Filed from a closed laptop

There is a particular kind of foolishness that everyone who has run a coding agent has committed at least once. You give it something substantial — port the importer to the new schema, work through the failing suite — and it settles in. Then the meeting starts, or the train is called, and you look at the lid of the laptop and understand that the lid is now load-bearing. So you sit there. You keep it open on your knees in the corridor. You have become a power supply.

The absurdity is not the agent. The agent is behaving well: it is a command-line program doing a long job. The absurdity is that a long job is pinned to the one computer in the building that gets carried around, closed, put to sleep, and taken through a tunnel.

Move the job off the laptop and the whole thing relaxes. It runs on the Mac mini on the desk, or a VPS, or a container werk provisions, or the cluster the company already pays for. Placement stops being an architecture decision and becomes an argument you pass. The lid closes. Nothing notices.

You dispatch from your own terminal. The work runs somewhere with power and a proper network. The commits come back.

What makes this tractable is that nobody has to invent a new interface for it. A repository already has two universal interfaces, and both of them predate every agent on the market: the terminal and git. People use them. Agents use them. Neither needs a plugin to be understood by the other. werk's whole argument is that if you make those two things trivially easy to reach — from any machine, from a browser, from someone else's browser — the rest of the workflow follows without being designed.

So: a fresh branch for every session, on whichever machine you named. A terminal that survives your laptop closing. And one list of every one of them, everywhere, that you can open from a shell or a browser tab.

What werk is

A single command that starts a process somewhere, puts your repository there on a fresh branch, and keeps the terminal alive after you have gone.

Bare werk prints the fleet and exits, the way ls or git status does. werk attach <name> puts you back inside a session. There is a TUI when you want to steer the fleet without leaving the terminal, and werk serve when you want the same thing in a browser.

In brief

One commandName a machine, name a job. werk clones the repository there, cuts a branch, starts the process and hands you the terminal.

One listEvery session on every machine, with its state and its last signal, in a shell or in a browser tab.

No integration per agentClaude Code, Codex, Gemini CLI, Aider. An agent released next month works on the day you install it.

Work arrives as gitEach session gets its own branch, so what comes back is history you can read, review and merge.

Part one  ·  On your own

Works today

Shut the lid. Come back Tuesday.

The first run is undramatic, which is the point. You are in your repository, in your own terminal, on your own laptop. You name a machine you can already reach — the mini under the desk, a VPS you keep, a container werk brings up for the occasion — and you name the job.

$ werk run --on studio-mini \ "claude -p 'port the importer to the new schema'" studio-mini repo cloned · branch werk/importer-schema session importer-schema · started · attaching

You watch it for a minute because the first time you always do. Then you detach, and this is the part that takes some getting used to: nothing happens. The process is not on your laptop. Detaching from it is no more significant than closing a window onto a room you have left.

Close the lid. Go to the meeting, get the train, sleep. The session is a process on a machine that is plugged in, and it stays a process on a machine that is plugged in.

Reattaching is the moment the product sells itself. The terminal is exactly where you left it, with two hours of work in the scrollback.

The list is the product

Once you have more than two of these, the list matters more than any one session. Bare werk prints the fleet and exits — every session on every machine, its state, and how long since it last said anything.

$ werk NAME WHERE STATE LAST SIGNAL importer-schema studio-mini running 3m ago docs-sweep vps-fra1 waiting 12m ago needs input flaky-test-hunt local done 1h ago exit 0 schema-migration k8s/dev running moments ago

werk attach importer-schema puts you inside that one. Or you run werk serve, open a browser on your own network, and get the same fleet as a web application — every session on every machine in one window, and you can type into any of them.

How it reads any agent at all

werk does not integrate with agents one at a time. It reads the signals a well-behaved terminal program already emits, and every serious agent is a well-behaved terminal program.

  • BELThe bell. Something wants you.
  • OSC 9
    OSC 777    Desktop notifications, so the fleet list can say what the session said.
  • OSC 9;4Progress, where a program reports it.
  • OSC 133Command boundaries and exit status — where a command started, stopped, and whether it worked.

Nothing on that list is werk's invention, and nothing on it is optional for a program that wants to behave in a terminal. That is why an agent released next month works on the day you install it.

Part two  ·  Two people, one terminal

Planned · not built

Hand somebody the live line.

Here is the situation this is for. A session has been going for an hour, it is deep in a migration nobody else has touched, and it has stopped on a question about a table that predates you. The person who knows the answer is two time zones away. You do not want to describe the terminal. You want them in it.

The plan is a link. You share the session, you send the link, and it opens in their browser onto the same live terminal you are attached to from your shell. Same scrollback, same cursor, same agent waiting on the same question. They type; you both see it. When they answer and drop out, you carry on where you were.

Not a recording, not a screen share, and not a copy. One session, two windows onto it.

The link is the unit, which means it can be scoped and it can expire. A share is for one session rather than for your machine, and it lasts as long as you say. Screen sharing gives away a whole desktop for the length of a call; a shared session gives away one terminal for half an hour.

Why this follows from the rest

werk serve already puts a live terminal inside a web page and lets you type into it. Sharing is that page, addressed to somebody else, with the reach to get to them and a boundary around what they can see. The hard part — a browser pane that is genuinely the terminal rather than a picture of it — is the part that exists.

What a share would be

One session, not a machine. One link, revocable. An expiry you set when you create it. A record of who was in it.

Everything above this line is design intent. None of it is built yet, and the drawing opposite is a drawing.

Part three  ·  The floor

Planned · not built

Every session in the building, on one sheet.

Ask an engineering organisation today what its agents are doing and you will get a shrug, a guess, and someone volunteering to go round the desks. The sessions exist, they are doing real work against real repositories, and there is no view of them. Each one lives inside one person's terminal on one person's machine.

The plan is a company-wide view: every agent session in the organisation on one page. Each person, the sessions they are running, and the subagents those sessions have spawned, because a session that fans out into six of its own is now the normal shape of a large job and is invisible from outside.

And then the part that makes it a view rather than a report: you open any one of them onto its live terminal. Not a status, not a summary written afterwards. The terminal, as it is, with the scrollback.

A tech lead should be able to see the whole floor, and then look at any one bench.

What it is good for

Knowing which sessions have been sitting on a question for forty minutes while their author is in a meeting. Seeing that three people started the same migration this morning. Watching a large job fan out and come back. Finding the run that produced a branch nobody can account for. All of it is the same primitive as part one — a fleet list with a live terminal behind every row — pointed at the organisation instead of at you.

The row and what is behind it

Person, session, machine, agent, state, age. Indented under a session, the subagents it spawned, with the same columns.

Behind every row, the live terminal. That is what distinguishes this from a dashboard: the drilldown is the session itself, not a card about it.

Planned. Not built. The drawing opposite is a drawing, and the names in it are invented.

Leader

The argument

Two interfaces, both older than the problem.

Every few years something arrives that needs a place to run, and the industry's reflex is to build it a bespoke home: a console, an orchestrator, a control plane with its own vocabulary. It is worth noticing that this workload does not need one. A coding agent is a program that reads a repository, writes to it, and talks over a terminal. Those are the same two interfaces a person uses, and they are the two interfaces every tool in the ecosystem already speaks.

That is the bet. Rather than integrate agents one at a time, take the two universal interfaces to a repository and make them trivially easy to reach: from your laptop, from a browser, from a colleague's browser, from a view of the whole company. The workload changes underneath and the surface does not. An agent released next month works on the day you install it, because werk did not need to know anything about it in the first place.

The first rung of that ladder is running now: dispatch, detach, reattach, one list. The rungs above it — reach from anywhere, a link you can hand somebody, the floor — are the same object seen from further away, and they are what we are asking to build next.

Try the part that exists.

Point werk at a machine you can already reach, dispatch something long, and close the lid. The rest of the argument makes itself when you come back to it in the morning.

$ werk run --on studio-mini "claude -p '…'" $ werk # the fleet, then exit $ werk attach <name> $ werk serve # the same thing, in a browser
