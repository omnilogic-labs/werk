# M6 — the `ghostty-ffi` adapter, the `xterm-oracle`, and the differential corpus

What the proposal's §7 M6 row asks: the two remaining adapters behind the
seam, `wp caps` across all three, and `wp bench` over the lot. The first
half is the adapters, the capability matrix, the compiled-binary result for
the ffi route, and the differential corpus (§6, "correctness,
differentially") with every disagreement it found attributed. The second
half, from [Performance](#performance) on, is the rest of `wp bench`: the
performance axis, the operational axis, the wasm trap isolation the
proposal's §8 asks about, and the soak.

The code is under [`../src/engine/ghostty-ffi/`](../src/engine/ghostty-ffi/),
[`../src/engine/xterm-oracle/`](../src/engine/xterm-oracle/) and
[`../bench/`](../bench/); the corpus is
[`../bench/corpus/`](../bench/corpus/). The three new runners are
[`../bench/perf.ts`](../bench/perf.ts) (`wp bench perf`),
[`../bench/ops.ts`](../bench/ops.ts) (`wp bench ops`) and

The two libghostty adapters are **four months of upstream apart**. That

between April and September, not loader defects.

## The ffi package

`libghostty-vt` 0.6.3, Apache-2.0 for the binding, MIT for the redistributed
libghostty binaries (`LICENSE_GHOSTTY`). `engines.bun >= 1.3.13`; Bun only,
through `bun:ffi`. The tarball is 18 MB, almost all of it prebuilds.

### Prebuilds

The README says six; the tarball has five. There is no `darwin-x64`, and no
Windows.

| Platform            | `libghostty-vt` | shim   |
| ------------------- | --------------- | ------ |
| `darwin-arm64`      | 1,342,296 B     | 51,016 |
| `linux-x64-glibc`   | 1,526,800 B     | 3,936  |
| `linux-x64-musl`    | 1,525,376 B     | 3,936  |
| `linux-arm64-glibc` | 1,342,432 B     | 4,328  |
| `linux-arm64-musl`  | 1,340,192 B     | 4,328  |

The shim exists because `bun:ffi` cannot pass structs by value; it wraps
libghostty's four by-value entry points with pointer-taking ones and is
linked against `libghostty-vt.so.0` with `RUNPATH $ORIGIN` (`@loader_path`
on darwin), so the pair has to sit in one directory under those names.
glibc versus musl is detected at run time from `process.report` with an ELF
`PT_INTERP` fallback.

Two things the daemon's own paths use — `decMode(1049)` for the alternate
screen, `cursor()` and `fullText()` for `wp logs` and `screen` — are there:
`mode("alt_screen_save")`, `snapshot().cursor`, and the plain formatter.

The binding's `snapshot().pwd` stayed `undefined` for every OSC 7 form
tried (`file://localhost/tmp`, `file:///tmp`, a bare path, the real
hostname) while the WASM adapter's `ghostty_terminal_get(PWD)` returned each
one, so there is no pwd to poll for either. Its `Terminal.renderToAnsiRect`
allocates a fresh `RenderState` per call, which consumes the terminal's
dirty flags; the adapter never calls it, and a daemon holding a consumer
must not either.

### `bun build --compile`

The proposal had this as untested. **The bare binding fails inside a
compiled binary** and the adapter makes it work:

- Bare: `LibraryNotFoundError: Bundled libghostty-vt missing at
/$bunfs/prebuilds/linux-x64-glibc/libghostty-vt.so`. The binding resolves
  its prebuild relative to `import.meta.url`, which is a bunfs path once
  compiled, and its `existsSync` check rejects it. The `.so` is not in the
  binary at all unless something imports it.
- Adapter: `bun.ts` imports all five prebuild pairs with
  `import ... with { type: "file" }`, which embeds them; when the resolved
  path starts with `/$bunfs/`, it writes the host platform's pair to
  `$TMPDIR/werk-poc-libghostty-vt-0.6.3/<platform>/` under the soname the
  shim was linked against (`libghostty-vt.so.0` next to
  `libghostty-vt-shim.so`) and calls `setLibraryPath` / `setShimLibraryPath`
  before the first dlopen. Written once, reused when present at the right
  size. `spikes/m6/compiled.test.ts` builds the binary, runs it from an
  empty directory with `PATH=/nonexistent`, and checks all three engines
  load; the ffi's library path in that run is the extracted one.

So the `.so` cannot be dlopened from inside the binary; it has to be on
disk, and the binary can put it there itself. That costs a temp directory
and one write per platform per machine, which is probably acceptable for a
daemon and worth a thought for a CLI that starts often.

| Binary                                      | Size    |
| ------------------------------------------- | ------- |
| An empty script                             | 90.2 MB |
| The WASM engine alone (M1's `embedded.ts`)  | 91.0 MB |
| All three engines (`spikes/m6/compiled.ts`) | 98.2 MB |

The 7.2 MB is the five prebuild pairs (7.1 MB) plus xterm. A build per
target would embed one pair, about 1.5 MB on x64.

`@xterm/headless` and both addons load inside the compiled binary without
any of this, which is what the proposal reported for 1.3.14 and holds.

### The daemon on `--engine=ghostty-ffi`

`wp run --engine=ghostty-ffi` reaches a `Session` on the ffi engine. The
daemon imports every registry entry (`engine/all.ts`) and constructs an
engine on first use, so an ffi library that cannot open costs nothing until
a session asks for it, and then the `run` is refused with the loader's own
reason (`engine "ghostty-ffi": libghostty-vt could not open its library:
…`) rather than a bare "no engine". `src/daemon/ffi-engine.test.ts` runs a
session on it, attaches, detaches, reattaches after output, and checks the
render (the binding's `toAnsiRect` with the cursor placed), `screen`, and
the alternate-screen flag.

Corpses restored from snapshot files are always on `ghostty-wasm`, since
only it can decode; an ffi session's snapshot is never written because
`encodeState` is `Unsupported`, so an ffi session does not survive a daemon
restart. That is the binding's gap, not the seam's.

## The oracle

`@xterm/headless` 6.0.0 with `allowProposedApi`, `reflowCursorLine: true`,
the serialize addon for `emitVt`, and the unicode11 addon with
`unicode.activeVersion = "11"`. Without the last, xterm's width table is
Unicode 6 and every emoji is one cell wide, which made the first corpus run
disagree with libghostty on every emoji; with it, the two agree on emoji
width and differ only where clustering and regional indicators are
involved (below). Grapheme clustering (DEC 2027) has no xterm equivalent
short of the graphemes addon, which is not loaded, so the oracle is always
2027-off.

Effects come through `parser.registerOscHandler` for 0/2 (title), 7 (pwd),
9 (notification, and 9;4 progress), 777 (notification), 133 (reported as
`other`), `onBell`, and `onData` for query replies. Handlers return false so
xterm's own handling still runs.

xterm's `write` is asynchronous: bytes are queued and parsed on a later
tick. The adapter queues writes and resizes in order and exposes
`flush(): Promise<void>`; the runner awaits it after every step. A reader
that does not is reading the previous state. Everything the corpus does not
compare returns `Unsupported("not a candidate; oracle only")`.

(vim, vim left open, `ls --color`, `bun install`, `top`, `htop`, `tmux`),
sixteen synthetic (`bench/corpus/README.md` lists each). Every case is an
asciicast; every output event is one `write`, so a recording's own PTY read
boundaries and a synthetic case's deliberate cuts are what the engines see.
Reattach cases end with a resize event and additionally run three restore
strategies per engine. Fuzz is 50 iterations each of random bytes and
random valid sequences from seed 1, each input fed in four random pieces,
and each engine also checked against itself fed the whole input.

without them: trailing whitespace is trimmed from every engine's
`plainText` (xterm's own trim keeps a written trailing space); a

and reported as a count; and identity replies (DA1 `CSI ?62;22 c` versus
`CSI ?1;2 c`, DA2 `CSI >1;0;0 c` versus `CSI >0;276;0 c`, and libghostty's

same fed in four random pieces as fed whole, on both libghostty commits and
on xterm. The four `interrupted-*` cases say the same for cuts placed on
purpose inside CSI, OSC, SGR and UTF-8. Whatever the differences below
are, none is a chunking bug.

### The disagreements, attributed

1. **`reflow-cursor-boundary`: three different answers.** Sixty characters
   on 40 columns, shrink to 20 with the cursor exactly at the wrap
   boundary, write `!`. The WASM (September) scrolls a row into history
   and puts `!` on a fresh line — exactly what a 20-column terminal that
   was never resized produces. The ffi (April) puts the cursor at column 0
   of the third row and `!` **overwrites the first `a`**. xterm puts the
   cursor at column 19 of that row without pending-wrap and `!`
   **overwrites the last `a`**. The WASM is right; the other two lose a
   character. The ffi's answer is an upstream change between the two pinned
   commits, which is what the proposal's "loader bug" rule cannot see — a
   June 2026 upstream commit guarding the wrap count when a column shrink
   pushes the cursor into scrollback is the likely one, though that was not
   confirmed by bisecting Ghostty. xterm's is a reflow defect of its own
   (`reflowCursorLine` puts the cursor on the last cell rather than past it).

2. **`c0-controls`: C0 bytes, again an upstream change.** The ffi's Ghostty
   stores 0x10–0x1F (bar ESC) as glyphs in cells; the WASM's ignores them;
   xterm ignores them. Both libghostty builds render a stray or invalid byte
   (0x80, 0x85, 0x9B, 0x9C, 0xC0, 0xFF on their own) as U+FFFD, which is
   Unicode's recommendation for a decoder; xterm drops such bytes silently.
   DEL is ignored by all three. This is why random-byte fuzz agrees 0 of 50
   on every pair: every random buffer has invalid UTF-8 in it.

3. **BCE cells through the ffi binding.** A cell erased with a background
   colour (`SGR 44` then `EL`) is a bg-colour-only cell in libghostty, its
   colour in the packed cell's content tag with no style. The binding's
   `RenderCell` reads only the style, so `styledCells` shows default
   background and `toAnsiRect` paints a plain space. The WASM adapter
   decodes the content tag and reports palette 4. This is a defect in the
   binding, visible in `reattach-primary` (row 9) and behind most of the
   9/50 cell agreement on sequence fuzz, which is full of `SGR 4x` followed
   by erases. The M1 finding that libghostty's own VT formatter drops BCE
   cells stands alongside it; the binding is worse, because the render
   state does carry the colour.

4. **Effects the binding does not have.** `agent-like` and
   `interrupted-osc` differ between WASM and ffi on effects only: the WASM
   reports OSC 9;4 progress and OSC 9 notifications, the ffi has no
   callback for either (nor for pwd). The WASM and the oracle agree on the
   full list for `agent-like`, including the progress state after a cut
   OSC 9;4 payload.

5. **Emoji width and clustering.** With the unicode11 addon, plain emoji
   and CJK agree. Regional indicators (`🇬🇧`) are two cells each in
   libghostty and one in xterm: UAX #11 gives them East Asian Width N, and
   xterm's table follows that; libghostty, like kitty and wezterm, treats
   Emoji_Presentation characters as wide. With 2027 on, libghostty joins a
   ZWJ family into one wide cell and a flag pair into one, per UAX #29;
   xterm has no clustering, so each component stays its own cell. With
   2027 off, the two agree on the family (three wide cells each) and
   differ only on the flags. libghostty also drops U+200B from a cell's
   text under 2027 where xterm keeps it as a zero-width codepoint; neither
   is visible.

6. **Hyperlinks are underlined in xterm's buffer.** A cell inside `OSC 8`
   reports `isUnderline()` in xterm.js; libghostty keeps the link separate
   from SGR. OSC 8 says nothing about underlining, so this is xterm's
   renderer convention leaking into its buffer model rather than a bug in
   either; it accounts for the `cells` differences in `interrupted-osc` and
   `reattach-primary` against the oracle.

7. **OSC 133;A mid-line.** libghostty moves to a fresh line when a prompt
   start arrives with the cursor past column 0, which is kitty's documented
   semantic-prompt behaviour and what Ghostty does; xterm.js has no OSC 133
   handler. Both libghostty builds agree. The fuzz grammar leaves OSC 133
   out for this reason and `osc133-prompt` records it.

8. **`CSI Ps s` with a parameter.** xterm.js treats `CSI 3 s` as save-cursor
   (SCOSC) and ignores the parameter; libghostty does not save. By xterm's
   own control-sequence reference, `CSI s` is SCOSC and `CSI Pl ; Pr s` is
   DECSLRM, so a parameterised `s` is a margin command (a no-op outside
   DECLRMM) and libghostty's reading is the conformant one. Found by fuzz
   (sequence #19, seed 1): a later `CSI u` restored different positions.

9. **A written space with a foreground.** After `SGR 30;41` and a space,
   libghostty's cell has the background and a default foreground; xterm's
   has both. Ghostty stores a space whose style is background-only as a
   bg-colour cell, an optimisation that discards the invisible foreground.
   Not visible; it is a share of the sequence-fuzz cell differences.

10. **Cursor at the pending-wrap position.** With the cursor past the last
    column, xterm reports `cursorX == cols`; libghostty reports `cols − 1`
    with a pending-wrap flag. A representation difference; the runner
    compares text, not cursor x, on the corpus pairs.

11. **The formatter styles the gap between two runs.** Not a pairwise
    disagreement but a reattach one, found by the two alternate-screen
    cases and described with them below: libghostty's VT formatter
    re-emits never-written cells between two styled runs as spaces under
    the first run's style, so an inverse status line grows an inverse bar
    across the blank cells after it.

12. **Not attributed.** One sequence-fuzz cell difference (a never-written
    cell after a tab carrying foreground 245 in xterm and none in
    libghostty) was not isolated: the same 25 characters in isolation
    agree, so it depends on earlier context in that input. Left as a lead.

Nothing in the corpus points at either loader. The two libghostty adapters
agree on every recorded program and on every synthetic case except the two
upstream-change cases and the binding's BCE and effects gaps.

### What the corpus says about the two reattach strategies

| case                    | engine       | re-emit, resize | resize, re-emit | state, resize |
| ----------------------- | ------------ | --------------- | --------------- | ------------- |
| vim-reattach            | ghostty-wasm | exact           | exact           | exact         |
| vim-reattach            | ghostty-ffi  | padding         | padding         | unsupported   |
| vim-reattach            | xterm-oracle | exact           | exact           | unsupported   |
| reattach-primary        | ghostty-wasm | differs         | differs         | exact         |
| reattach-primary        | ghostty-ffi  | differs         | padding         | unsupported   |
| reattach-primary        | xterm-oracle | differs         | exact           | unsupported   |
| reattach-primary-shrink | ghostty-wasm | exact           | exact           | exact         |
| reattach-primary-shrink | ghostty-ffi  | differs         | padding         | unsupported   |
| reattach-primary-shrink | xterm-oracle | exact           | exact           | unsupported   |
| reattach-alt-counter    | ghostty-wasm | differs         | differs         | exact         |
| reattach-alt-counter    | ghostty-ffi  | padding         | padding         | unsupported   |
| reattach-alt-counter    | xterm-oracle | differs         | exact           | unsupported   |
| reattach-alt-vim-like   | ghostty-wasm | differs         | differs         | exact         |
| reattach-alt-vim-like   | ghostty-ffi  | padding         | padding         | unsupported   |
| reattach-alt-vim-like   | xterm-oracle | exact           | exact           | unsupported   |

`exact` is text, cells and cursor identical to the never-detached terminal;
`padding` is the same modulo never-written cells the re-emission wrote as
spaces; `differs` has the detail in the run's output.

**Primary screen.** State transfer is exact in every case, as M2 found.
Re-emission then resize fails exactly when the source held soft-wrapped
rows at emission time (`reattach-primary`, growing from 60 to 100: the
source rejoins its paragraph, the copy's hard newlines do not, and the
copy's rows shift) and is exact when it did not
(`reattach-primary-shrink`, eight 70-column lines shrinking to 50: both
wrap the same way afterwards). **Resize first, then re-emit at the new
size** — the CLI's proposed fix — gives text and cursor exactly in every
primary-screen case on both libghostty adapters and the oracle. Its one
loss on the WASM is the M1 formatter defect: the BCE row comes back
default-background. On the ffi it is `padding` only, because `toAnsiRect`
carries BCE colours but writes every cell. So for a CLI reattach on the
primary screen the strategy is probably exact enough to ship, with the
formatter's BCE gap as the known cost until upstream's formatter carries
bg-only cells.

The ffi's re-emit-then-resize is `differs` on both primary cases for a
reason of its own: `toAnsiRect` pads every row to the full width with
written spaces, so a later shrink reflows those spaces as content. A
re-emission meant to survive a resize wants the formatter's shape (rows
ending where the content ends), not a painted rectangle.

**Alternate screen.** libghostty's header says the alternate screen does
not reflow, and the corpus agrees: the counter TUI and the vim-shaped
screen resized from 40×10 to 60×14 keep their cells where they were on
every engine, and the copies, which a re-emission puts on the _primary_
screen (it carries no `1049`), keep theirs too because nothing in them is
soft-wrapped. The real vim recording is `exact` under all three strategies
on the WASM. The two synthetic alternate-screen cases are `differs` for the
WASM's re-emission, both ways, for a reason that is neither reflow nor
padding: **the VT formatter emits never-written cells between two styled
runs as spaces under the first run's style.** `SGR 7` `AB`, cursor to
column 10, `C` comes out as `ESC[7mAB       ESC[0mC`, so the copy has an
inverse bar where the source has blank cells; the same with a foreground
colour is invisible but the cells differ. Written spaces between runs are
fine (`AB   C` under one style round-trips). On the vim-like status line
(`SGR 7 " file.txt  2L, 34B " SGR 0`, then `2,1` further along) the bar is
visible; on the counter it is a yellow-foreground gap nobody can see. This
is a fourth formatter defect alongside M1's three (soft wrap, BCE, closed
hyperlinks), it affects any TUI with styled runs separated by unwritten
cells, and the ffi's `toAnsiRect` does not have it (its `padding` results
are plain spaces). The binding is not the fix, but the shape it uses —
reset before a blank run — is what the formatter probably wants upstream.

Two things follow for the daemon. A full-screen program's reattach is
exact in content by any route, because nothing reflows. And the copy sits
on the wrong screen: a daemon that re-emits an alternate-screen session
and later relays the program's `CSI ? 1049 l` will have the client's
terminal restore a primary screen it never saw. The daemon probably wants
to emit `CSI ? 1049 h` before the screen when the source is on the
alternate screen, and the corpus can check that once it does. xterm's
re-emission of the counter TUI places the cursor one cell off after the
resize (`26,8` against `27,8`), a serialize-addon detail rather than an
emulation one.

# Performance

`wp bench perf` (`bench/perf.ts`), every measurement on each engine that
loads and has the capability. Bun 1.3.14, kernel
`6.18.33.2-microsoft-standard-WSL2`, Intel Core i9-14900HX, WSL2. Two
things to keep in mind reading the two libghostty columns: the ffi is **four
months older upstream** than the WASM (`e88c6c09` in April against
`3c1ef5b3` in September), so a wasm-versus-ffi gap is native-versus-WASM
_plus_ whatever changed in libghostty between the two; and the ffi's
scrollback is a byte cap approximated from the line count (`lines × 1 KiB`),
so a like-for-like memory comparison would want both set explicitly. The
oracle is in the tables because the runner runs it, but it is the
differential reference, not a session engine — nothing in the daemon runs
`xterm-oracle`.

## Relay latency

A byte written by a client, through the real daemon's socket to a raw
no-echo `cat` under a PTY and back, timed to the echo; 2,000 iterations, the
first tenth dropped. The same process also runs M0's bare in-process PTY
round trip (no socket, no daemon) for a same-run floor. Round trip,
microseconds:

| Path                                 | n    | p50   | p90   | p99   | max    |
| ------------------------------------ | ---- | ----- | ----- | ----- | ------ |
| bare PTY, in-process (M0 path A)     | 1800 | 61.2  | 74.4  | 133.7 | 1210.5 |
| client → daemon → PTY → cat → client | 1800 | 108.6 | 145.0 | 240.4 | 1592.5 |

`dtach` is **not installed** and no system package was added, so the
proposal's `dtach` floor is not measured here; the bare-PTY row is the floor
this run has, and it reproduces M0's 61–66 µs. The real daemon adds about
**47 µs at p50** and 107 at p99 over that floor. M0's bare Bun relay added
4–8 µs, and the difference between the two is what the daemon does that the
relay did not: frame the byte on the client, parse and dispatch it on the
daemon, feed the echo through libghostty, encode an output frame, queue it
through the per-connection backpressure accounting, and parse it again in
the client library. Fifty microseconds for that is a fraction of one frame at
any refresh rate a human notices; the p99 carries a busy event loop and the
WSL2 scheduler. Latency in this path is not the constraint on the design,
as M0 concluded, and the daemon's own overhead over the relay is now a
number rather than a guess.

The §8 threshold is **~5 MiB idle per session**. An idle `sh` session costs
**0.7–0.9 MiB of daemon RSS** (fifty of them: 110 MiB in total, 51 above
the empty daemon, of which 30 MiB is the wasm instance and the rest the JS
heap's per-session objects and Bun's PTY plumbing). The first session is
dearer, 11 MiB, because it loads and compiles the wasm engine. A session that
has scrolled a megabyte of `seq` through its PTY and holds its 2,000-line
cap costs about **1.1 MiB** (the wasm column grows 1.2 MiB per such session,
the cap's pages). Both are a fifth of the threshold. The `seq` rows start
from the RSS the idle fleet left behind, since the wasm instance never gives
memory back once grown — that is the negative "delta" on the 10-session row,
not a saving.

**Churn is the one place the PoC saw growth.** Three rounds of killing and
re-creating the fifty `seq` sessions add about 1.3 MiB of RSS and 3 MiB of
wasm memory per round, and a forced `Bun.gc(true)` changes nothing, so it is
not uncollected JS. Eight rounds in a separate probe were perfectly linear —
RSS 152 → 164 MiB, wasm 76 → 104 MiB, and 107 MiB with every session removed
at the end — which is ~64 KiB, one libghostty page, per terminal lifetime.
It reproduces in-process with no daemon at all: fifty terminals fed 150,000
lines each, freed, eight times, grow the instance by 3.1 MiB a round. But it
is **not** a function of how much scrolled: the same probe at 3,000 lines,
at 300,000 and at 600,000 is flat to the byte across eight rounds, and M1's
create-and-free rounds were flat too. It depends on the terminal's page
layout at the moment it is freed — deterministic for a given stream, absent
for most streams — which reads like a page-pool or size-class artefact in
libghostty's wasm allocator rather than a missing free in the adapter
(`dispose` releases everything it allocated and the flat cases prove the
path). Whether it is bounded is not settled by eight rounds. At 64 KiB per
affected session it takes some fifteen hundred such lifetimes to cost 100
MiB, and a product that recycles its instance — instance-per-session, which
the trap section below wants anyway, or a periodic re-instantiation — would
never see it; but it is the kind of thing the 24-hour soak with churn in it
is for, and worth a report upstream once the trigger is narrowed.

## Trap isolation

The proposal's §8 row: "a wasm trap in one session poisons the shared
instance → instance-per-session at ~450 KiB each". This matters because the
daemon holds **one** `WebAssembly` instance for `ghostty-wasm` and every wasm
session's terminal lives in it (`getEngine` returns one engine;
`Session.create` calls into it), so a poisoned instance is every wasm session
at once.

Each deliberate fault runs on its own fresh instance with a second terminal
live beside the target, and afterwards the other terminal and a
freshly-created one are checked against a terminal on an untouched instance:

| Single fault (own instance)                            | Outcome                                                             | Time    | Other terminal ok | Fresh terminal ok | wasm memory |
| ------------------------------------------------------ | ------------------------------------------------------------------- | ------- | ----------------- | ----------------- | ----------- |
| vt_write, handle far outside memory (0xFFFFF000)       | RuntimeError: Out of bounds memory access (evaluating 'f(...args)') | 0.14 ms | yes               | yes               | 4.4 MiB     |
| vt_write on a live terminal, input pointer past memory | RuntimeError: Out of bounds memory access (evaluating 'f(...args)') | 0.15 ms | yes               | yes               | 4.4 MiB     |
| resize to 0x0                                          | returned -2 (INVALID_VALUE)                                         | 0.13 ms | yes               | yes               | 4.4 MiB     |
| vt_write on a freed handle (use after free)            | RuntimeError: Out of bounds memory access (evaluating 'f(...args)') | 1.81 ms | yes               | yes               | 4.4 MiB     |
| terminal_free on a freed handle (double free)          | returned 0 (SUCCESS)                                                | 0.78 ms | yes               | NO                | 3.8 MiB     |

Then the same trapping call is repeated on one instance until a fresh
terminal on it stops working, and the absurd resize is run in a child process
under a 30 s timeout because it may never return.

```
repeating the bogus-handle trap poisons the instance after 7 repeats: a fresh terminal on it then throws.
resize to 65535×65535, in a child process: returned -1 (OUT_OF_MEMORY) after 1629 ms; the child's RSS peaked at 3290.2 MiB
daemon's PTY hot path wraps vt.write in try/catch: yes (a single trap in one session's write is swallowed; the shared instance is the exposure).
```

**What this says.** A _single_ trap does not poison the shared instance — the
other terminal and a fresh one keep working, byte-for-byte identical to a
terminal on an untouched instance, after a bogus handle, an input pointer
past the end of memory, and a use-after-free that happened to trap. A
resize to 0×0 is refused with `INVALID_VALUE`. But the instance is **not
durable against faults**. Repeating the same trap poisons it after **seven**
repeats: a trap unwinds the JavaScript frames but not the module's own
shadow-stack pointer (a wasm global the compiled Zig adjusts on entry and
restores on return, and a trap skips the return), so each trap leaks a frame
and the seventh pushes the next call off the end of the stack region into an
out-of-bounds access, after which every call into the instance throws. A
**double free** returns `SUCCESS` and poisons the allocator: the next
`create` throws. And the use-after-free is undefined behaviour in the honest
sense — in this run it trapped, in an earlier probe the same call returned
`SUCCESS` and the instance carried on. The absurd resize did not hang: the
child grew the instance to 3.3 GiB in 1.6 s and then got `OUT_OF_MEMORY`
back, cleanly (an earlier probe of the same call, taken while the soak was
running, had not returned after 90 s — so "cleanly" depends on the host
having the 3 GiB to give, and a daemon that accepted a client's resize
unchecked would hand any client a 3 GiB allocation on demand).

The crucial qualifier is where these faults come from: **parsing arbitrary
PTY bytes never traps** — the differential fuzz corpus feeds random bytes and
random valid sequences and libghostty renders U+FFFD rather than faulting,
and no corpus case traps. So a session cannot poison the instance with its
_output_; only a control-flow bug in werk's own handle management (a
use-after-free of a handle, a double-dispose, a resize with unchecked
dimensions) can. The daemon's PTY hot path already wraps `vt.write` in
`try/catch`, so a single throwing write is swallowed and only that session's
screen stops updating — but the shared instance is the exposure, and the
proposal's **instance-per-session** (or a supervised worker per instance) is
the sound answer to it: it turns "one werk bug takes down every wasm
session" into "one session", and it would also retire the churn residue the
memory section found. The ~450 KiB per instance the proposal cites is the
price, and the memory table above says the daemon has the room. Clamping
resize dimensions at the daemon's edge is the cheap fix for the third fault
whichever way the instance question goes.

| 25  | 107.9 MiB | 30.9 MiB | 83.1 MiB | 6.0 ms           | 12.4 ms         | 1.0 ms     | 11.2 ms       |
| 30  | 108.2 MiB | 30.9 MiB | 69.3 MiB | 6.3 ms           | 12.4 ms         | 0.6 ms     | 9.1 ms        |

**RSS is flat.** It climbs from 86 to 105 MiB inside the first minute — the
ten noisy producers filling their 2,000-line scrollbacks, which is the wasm
column going from 13 to 30 MiB and stopping there by minute 7 — and then sits
between 105 and 109 MiB for the remaining twenty-nine. The second-half fit is
slightly negative; the whole-run figure is that first minute divided by half
an hour, not a trend. Against the daemon's own inputs over that time (about
88 MiB of PTY output parsed and relayed to the snapshot-mode replica, 30
snapshot passes writing ten files each, 139 attach-and-detach cycles) nothing
accumulates. The JS heap saws between 65 and 120 MiB `heapUsed` as JSC
collects on its own schedule, with no rising floor.

**Nothing degrades.** Attach latency in the last quarter is the same as the
first (p50 0.8 ms against 0.7, p99 2.6 against 2.2); the worst event-loop
stall in the whole run is 12.4 ms and it happens in the first six minutes,
after which the total maximum never moves; the snapshot pass holds the loop
for about 10 ms every 30 s to encode and write ten ~600 KB files. All twenty
children are still running at the end and the snapshot-mode replica never
lagged.

This is thirty minutes, not twenty-four hours, and the shape it shows — a
fill, then a plateau — is the shape one would want to see hold for a day.
The one thing worth carrying forward is that the wasm instance's memory
never shrinks: libghostty keeps its pages once grown, so the plateau is set
by peak scrollback across all sessions rather than current. That is bounded
by the per-session cap and the session count, and it is not a leak, but a
day-long run with churn in it is what would confirm that it stays bounded.

## The 24-hour run is not taken

The proposal's actual question is 24 hours, and **it is not answered here** —
a 24-hour run does not fit inside this task. The runner is ready for it and
the command is:

```console
$ wp bench soak --duration 24h --interval 60s --out soak-24h.jsonl
$ wp bench soak --report soak-24h.jsonl        # the summary, any time after
```

It writes one JSONL line a minute (about 1,440 lines, a couple of hundred KB)
and its own daemon's log beside it, both on temp dirs; the summary can be
regenerated from the log without re-running. Point-in-time throughput is not
what would disqualify a JavaScript daemon — the 30-minute slope is small and
flattening — but only the day-long run settles the row, and it is the one
measurement in the whole PoC that a short sitting cannot stand in for.

# M6 verdict

M6 has no stop condition; its job was to build the last two adapters and run
`wp bench` over everything, and that is done. Reading the four axes against
§8:

- **Throughput** clears the 20 MiB/s threshold several times over on both
  session engines.
- **Memory** is far under the 5 MiB-idle threshold, one shared wasm instance
  across sessions, and **churn does not leak**.
- **The slow client** is caught before its queue crosses the bound, as M2
  found.
- **Trap isolation** is the one row that does not simply clear, and it clears
  in werk's favour with a caveat: the shared instance shrugs off anything a
  session's _output_ can do (no PTY byte stream traps it) and survives a
  single trap of any kind tried, but seven repeated traps, a double free, or
  an unchecked resize will take it — and it is fragile only to a control-flow
  bug in werk's own handle management, for which instance-per-session is the
  sound, affordable mitigation.
- **Churn** leaves ~64 KiB in the wasm instance per terminal lifetime for
  some streams and none for others, linear over eight rounds; the one growth
  the PoC saw, small, and one instance-per-session would also retire.
- **The soak** shows a small, flattening RSS slope over 30 minutes with
  bounded event-loop lag; the 24-hour run the proposal names is left ready,
  not taken.

Everything here is one machine, one kernel, WSL2, Bun 1.3.14, and
`linux-x64-glibc`. macOS and Windows are not covered, the ffi's other four
platforms are claims not measurements, and the transport's loss-and-reorder
behaviour and the day-long soak are the named gaps. Within that boundary,
nothing M6 measured moves the design the proposal describes.

## Notes for whoever runs these again

- **Loading each engine.** `import "../src/engine/all.ts"` registers all
  three; `getEngine(id)` constructs one lazily and `peekEngine(id)` returns
  it only if already built (for `stats`). `ghostty-ffi` can reject (no
  prebuild for the platform, a compiled binary without the extraction path);
  catch it and run without, as every runner does.
- **The oracle's writes** are queued; `await term.flush()` before reading,
  and the throughput loop silences xterm's per-DEL parser logging while
  timing. The libghostty adapters are synchronous.
- **The benches never touch the real daemon.** Each runs its own on temp
  runtime and state dirs (`bench/_lib.ts`'s `tempDaemon`), shuts it down, and
  removes the directories; `pgrep -af __daemon` is empty afterwards. The soak
  keeps the machine usable by rate-limiting its producers.
- **`wp bench ops` compiles.** A full run compiles five binaries into
  `dist/bench-ops/` (~2–3 min); `--no-compile` reports on whatever an earlier
  run left. `--quick` on any runner is the smoke-test path: tiny parameters,
  no compiles.
- **The corpus is reusable** for a soak's correctness check:
  `runDifferential({ cases: [...] })` returns a `Report`;
  `differential.test.ts` shows the shape.
