# M3 — snapshots to disk, corpses on restart, and one `tip` commit decoding another

What the proposal's §7 M3 row asks: encode every session to disk on a timer
and on `SIGTERM`, restore on start with the two-stage `READY` decode, then
encode on one `tip` commit and decode on the next two. The stop condition is
"the snapshot cannot be round-tripped, the decoder's prefix is not
renderable, or no two adjacent `tip` commits agree" — **not hit**. The
evidence is in [the restore numbers](#restore-on-start-corpses-and-the-two-stage-decode)
and [the cross-commit table](#one-tip-commit-decoding-another).

The code is under [`../src/daemon/`](../src/daemon): the file format in
`snapshot.ts`, the corpse construction path in `session.ts`, the timer and
the restore pass in `server.ts`. Tests drive real daemons in temporary
runtime and state directories with the timer at one second
(`daemon/snapshot.test.ts`); the cross-commit and cost measurements are
scripts under [`../spikes/m3/`](../spikes/m3). `bun test` is 130 across 13
files in about 27 s, and no daemon, snapshot file or `wp attach` is left
behind. A Bun hazard M2 left open was pinned down on the way; it is at the
end, [before the verdict](#a-bun-finding-a-pipe-fd-closed-by-hand-kills-a-later-socket).

## The snapshot file

One file per session, `$XDG_STATE_HOME/werk-poc/<id>.snap` (falling back
to `~/.local/state/werk-poc/`; `WP_STATE_DIR` overrides it, which is how the
tests keep out of the real one). The state directory is separate from the
runtime directory on purpose: `$XDG_RUNTIME_DIR` is tmpfs and cleared on
logout, and a snapshot has to outlive both.

```
┌──────────────────────────────┬────┬──────────────────────────────┐
│ one line of JSON (the header)│ \n │ the GHOSTSNP bytes, verbatim │
└──────────────────────────────┴────┴──────────────────────────────┘
```

The header carries `wp` (the PoC version), `engine` (`ghostty-wasm`),
`ghostty` (the libghostty commit whose encoder produced the bytes), and the
session's `id`, `argv`, `cwd`, `cols`, `rows`, `createdAt`, `title`, `pwd`,
`status`, `exitCode`, `signalCode`, `exitedAt`, plus `snapshotAt` (when the
file was written), `corpse` (set when the session was itself a restored
corpse) and `bytes` (the length of what follows). One file rather than two
so that a single `rename(2)` is the whole commit: the header names the
encoder commit, and a header without its bytes would be a torn snapshot. The
JSON never contains a raw newline, so the first `\n` is the boundary. The
write is temp file → `fsync` → rename, 0600, in the same directory; a crash
mid-write leaves the previous file intact. A file whose header parses but
whose byte count is wrong or whose bytes do not begin with `GHOSTSNP` is
logged and left in place, not decoded (tested with a torn file).

The header for an idle 60×12 shell is 436 bytes; the `GHOSTSNP` payload
behind it is 1,178. So the file is about a third header for a small
session and almost all payload for anything with scrollback.

## When snapshots are taken, and what the detached daemon does on `SIGTERM`

| Trigger                         | What is written                                                                                                         | Measured                                                                                                                                                    |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Timer (30 s default)            | Every session whose emulator has consumed bytes since its last snapshot (a `dirty` flag set in the PTY `data` callback) | An idle shell is written once and then never again while idle; typing `echo three` gets it rewritten on the next tick                                       |
| Child exit                      | The session once more, after the PTY's last bytes are in, so the final screen and exit code are kept                    | `echo bye; exit 3` → header `status: exited`, `exitCode: 3`; the bytes decode to a screen containing `bye`                                                  |
| `shutdown` request              | Every session, dirty or not, before the children are killed                                                             | 2 sessions in 0.9–1.1 ms                                                                                                                                    |
| `SIGTERM` / `SIGINT` / `SIGHUP` | The same shutdown path                                                                                                  | A real `SIGTERM` to the detached daemon's pid: `shutting down: SIGTERM`, `shutdown snapshots: 1 of 1`, process gone, file present with the `GHOSTSNP` magic |
| `kill --rm`                     | The file is deleted along with the session                                                                              | Tested for an exited session and for a corpse                                                                                                               |

**`process.on("SIGTERM")` fires inside the detached daemon.** M0 established
Bun's signal handling in general; the daemon is `setsid`'d with no tty and
`stdio` on `/dev/null`, and the handler runs there exactly as in a foreground
process. The test sends the signal with `process.kill(pid, "SIGTERM")` with
the timer set to 60 s so that nothing but the signal path can have written
the file.

Corpses are never re-encoded: their screen cannot change and their file is
already on disk, so a daemon holding twenty restored sessions does nothing on
its ticks (`written.timer` stays 0, the file's mtime does not move).

The `dirty` flag is coarse — a byte that changes nothing visible still
counts — but it means an idle fleet costs nothing, and a session under
continuous output is encoded once per tick however much it wrote.

## What a snapshot costs

Encode is synchronous, so "encode time" and "how long the timer holds the
event loop for that session" are the same number. Measured with
`spikes/m3/snapshot-cost.ts` on the engine the daemon runs, five encodes
each (the spread is cold versus warm JIT):

| Session                                      | Rows  | Bytes   | Encode min / median / max | `ready()`         | history          | Round trip |
| -------------------------------------------- | ----- | ------- | ------------------------- | ----------------- | ---------------- | ---------- |
| Idle shell, 3 lines                          | 24    | 1,191   | 0.20 / 0.50 / 1.22 ms     | 2.62 ms, 24 rows  | 0.21 ms, 0 pages | identical  |
| 3,000 plain lines (2,000 kept)               | 1,653 | 12,720  | 0.20 / 0.40 / 0.49 ms     | 1.36 ms, 305 rows | 0.95 ms, 2 pages | identical  |
| 3,000 styled lines (2,000 kept)              | 1,653 | 115,375 | 0.19 / 0.31 / 4.87 ms     | 1.46 ms, 305 rows | 1.03 ms, 2 pages | identical  |
| 3,000 dense styled 80-col lines (2,000 kept) | 1,653 | 936,416 | 0.78 / 0.92 / 4.11 ms     | 1.31 ms, 305 rows | 3.06 ms, 2 pages | identical  |
| 10,000 plain lines (2,000 kept)              | 1,913 | 14,541  | 0.06 / 0.07 / 0.13 ms     | 0.89 ms, 565 rows | 0.70 ms, 2 pages | identical  |

And for the timer's worst case, every session dirty in the same tick:

| Fleet in one tick             | Total bytes | Event loop held |
| ----------------------------- | ----------- | --------------- |
| 10 × idle shell               | 11,910      | 0.20 ms         |
| 10 × 3,000 plain lines        | 127,200     | 1.24 ms         |
| 10 × 3,000 dense styled lines | 9,364,160   | 8.78 ms         |
| 50 × 3,000 plain lines        | 636,000     | 5.91 ms         |

Inside the daemon the numbers agree: the idle shell's timer snapshot is
1,178 B in 0.15–1.6 ms, the `seq 1 3000` session's is 12,722 B in
0.6–1.8 ms, and the write (`fsync` included) adds 0.1–0.6 ms. Two things
stand out. **Size is driven by styling, not rows** — the same 1,653 rows are
12.7 KB plain, 115 KB with an SGR run on some lines, and 936 KB when every
cell carries its own colour — while **encode time barely moves**: under a
millisecond warm for all of them, which looks like the encoder copying
pages rather than walking cells. So the timer's cost is bounded by disk
bytes, not CPU; a fleet of fifty plain sessions holds the loop for 6 ms
every 30 s, and even ten worst-case sessions hold it for under 10 ms. The
PTY `data` callback never waits on any of this beyond that hold; a product
that wanted to be stricter could encode one session per tick, but nothing
here says it needs to.

## Restore on start: corpses, and the two-stage decode

At start, before the socket is bound, the daemon reads every `.snap` in the
state directory and constructs a `Session` through its second path:
`Session.restore(header, bytes, engine)`. No child, no PTY; the emulator
comes from `engine.decodeState(bytes)`. `ready()` is called first, which
gives a terminal with the active screen and the newest page of scrollback
and makes the session attachable; then `next()` is driven to completion,
synchronously, and both phases are timed and reported through `ls` as
`restore: { readyMs, historyMs, readyRows, totalRows, pages, snapshotBytes }`.

From the test's `seq 1 3000` session, 12,722 bytes:

| Phase                     | Time         | State                                                   |
| ------------------------- | ------------ | ------------------------------------------------------- |
| `decodeState` + `ready()` | 1.9–3.8 ms   | 305 rows renderable: the 24-row viewport plus one page  |
| `next()` to FINISH        | 0.76–0.94 ms | 2 pages, 1,653 rows                                     |
| Whole restore pass        | 13–14 ms     | 2 files, **including** the engine's first instantiation |

The test asserts the split: `readyRows` (305) is below `totalRows` (1,653),
`pages` is 2, and the screen and `logs` of the corpse are byte-identical to
the `screen` and `logs` requests recorded before the shutdown, cursor
included. The small session shows the other side of the split — `ready()`
holds all 12 rows and `pages` is 0 — as M1 said it would for anything under
a page. The render frame a corpse sends on attach is the same bytes a live
attach produced before the restart.

Driving the history synchronously at start is fine here because it costs a
millisecond and the socket is not yet listening. A product would probably
not do it that way: `ready()` is all a first paint needs, and history could
be pulled on first attach, on a timer, or never for a corpse nobody opens.
The seam already supports that — `next()` is incremental and `ready()`'s
terminal is usable between pages.

### The mismatch rule, as implemented

If a file's `ghostty` commit is not the daemon's `GHOSTTY_COMMIT`, the
bytes are not handed to the decoder at all. The session is still listed, as
`corpse` with `corpse: { reason: "mismatch", snapshotEngine, daemonEngine }`,
so the user can see what they had, and `attach`, `logs` and `screen` return
a one-line notice naming both commits rather than a screen. The file is not
rewritten (there is nothing to write), it survives further restarts
unchanged, and `kill --rm` removes it. That is §3's rule — say plainly that
the two ends differ, do not bridge — applied to the one place a daemon meets
bytes from another build. The test writes a real snapshot's bytes under a
header with a foreign SHA and checks all of it.

## The corpse from the CLI

| Command             | What a corpse does                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wp ls`             | `STATUS` is `corpse`, or `corpse(mismatch 01234567/3c1ef5b3)`; a new `SNAPSHOT` column says when the file was last written (`9s ago`, `-` for a live session not yet written); the original command is shown                                                                                                                                                                                                                            |
| `wp attach <id>`    | The viewport is painted from the corpse's emulator exactly as for a live session, then one inverse-video line on the bottom row: `[corpse: snapshotted 2s ago, read-only; ctrl-\ to leave] sh -c …`; for a mismatch, `[corpse: not decoded, ghostty 01234567 vs this wp's 3c1ef5b3; ctrl-\ to leave]`. `--read-only` is implied; the attacher's size is ignored (the emulator keeps the snapshot's size, and there is no child to tell) |
| typing into it      | Dropped at the daemon; the connection is told once, with a `notice` message the CLI paints on the bottom row: `input ignored: this session is a snapshot, read-only`                                                                                                                                                                                                                                                                    |
| `ctrl-\`            | `[detached <id>]`, as for a live session; the corpse stays listed                                                                                                                                                                                                                                                                                                                                                                       |
| `wp logs <id>`      | The whole screen with scrollback, as before                                                                                                                                                                                                                                                                                                                                                                                             |
| `wp kill --rm <id>` | `removed <id>`; the file is gone                                                                                                                                                                                                                                                                                                                                                                                                        |

The bottom-row banner uses save-cursor / `CUP` / restore-cursor so the
painted screen and the cursor stay where the snapshot put them; on a corpse
nothing ever paints over it. Whether a product wants a banner, a status
line, or a different colour for the whole screen is a design question; the
mechanism is one line of VT.

## The `snapshot` request

`{ t: "snapshot", id }` returns the session's emulator as `GHOSTSNP` bytes,
base64 in the JSON reply, with `ghostty` (the encoder's commit), `cols`,
`rows` and `encodeMs`. It is a read, not a checkpoint: it does not touch the
file or the `dirty` flag. The client library decodes the base64 and hands
back a `Uint8Array`; the test decodes it in-process with the same engine and
gets the daemon's `screen` text and cursor. 1,195 bytes in 0.27 ms for the
idle shell. This is what a browser running the same libghostty will ask for
in M4, so it exists now; a binary frame type instead of base64 would be the
obvious change if the JSON becomes the cost.

## One `tip` commit decoding another

§3's worry is that `GHOSTSNP` format version 1 carries no
binary-compatibility promise across `tip` builds. The measurement asked for
is "encode on one commit, decode on the next two".

**Which commits.** The pin, `3c1ef5b3`, is the head of `main` as of this
milestone (2026-09-01 17:25), so no later `tip` commit exists to decode on.
`tip.files.ghostty.org/<sha>/ghostty-vt-small.wasm` exists only for commits
CI built it for — probing with `HEAD` walking back through `main`, the
builds found were `81681158` (2026-08-31 21:23), `2c854a1a` (20:17, the
commit that added freestanding support), and `c2906398` (17:14); `20abdb50`,
`b7a680bc` and `4b51f521` have no artifact despite two of them having a
successful `release-tip.yml` run. They were fetched with
`vendor/ghostty-vt/fetch.ts <sha> --no-headers` and stay gitignored. So the
run is "encode on one commit and decode on the next two" read backwards
from the pin: three distinct builds, each decoding the other two in both
directions, with the same-build decode as the control.

| Build      | Commit                    | Artifact                      | `library_version` | Exports |
| ---------- | ------------------------- | ----------------------------- | ----------------- | ------- |
| `c2906398` | 2026-08-31 17:14          | 711,364 B, sha256 `99f82143…` | 0.1.0-dev         | 181     |
| `2c854a1a` | 2026-08-31 20:17          | 709,743 B, sha256 `e0a7d6c6…` | 0.1.0-dev         | 181     |
| `81681158` | 2026-08-31 21:23          | 738,713 B, sha256 `df0cf5b0…` | 0.1.0-dev         | 189     |
| `3c1ef5b3` | 2026-09-01 17:25, the pin | 738,713 B, sha256 `df0cf5b0…` | 0.1.0-dev         | 189     |

`81681158` and the pin are **byte-identical** artifacts — the commits between
them touched translations and macOS — which is itself worth knowing: a
`tip` SHA changes on every merge, the WASM only when libghostty-vt does.

**`ghostty_type_json` across the builds.** `c2906398` → `2c854a1a`: no
difference. `2c854a1a` → `81681158`: six types **added** —
`GhosttySelectionBuffer`, `GhosttySearchData`, `GhosttySearchOption`,
`GhosttySearchScroll`, `GhosttySearchStatus`, `GhosttySearch` (the terminal
search C API landed in `4b51f521`). No type was removed or changed; every
struct layout, enum value and bitfield the M1 loader reads is the same on all
four builds. The loader built on the pin loaded all three older builds
without complaint.

**The decodes.** Three cases encoded on each build and decoded on each build,
compared on viewport text, styled cells, cursor, the whole screen with
scrollback, the alternate-screen mode, and size; then the restored terminal
was encoded again (a corpse must be carried forward), and for the two cases
with a follow-up (`CSI ? 1049 l` to leave the alternate screen; `1mX` to
finish the pending CSI) both terminals received it and were compared again.

| Case                                                 | Bytes   | `c2906398` → others | `2c854a1a` → others | `3c1ef5b3` → others | Backwards (others → `c2906398`) |
| ---------------------------------------------------- | ------- | ------------------- | ------------------- | ------------------- | ------------------------------- |
| Styled 80×24 with 3,000 lines of scrollback          | 115,810 | identical           | identical           | identical           | identical                       |
| Alternate screen, primary intact underneath          | 1,829   | identical           | identical           | identical           | identical                       |
| Mid-CSI continuation (`ESC [ 3` pending), then `1mX` | 1,092   | identical           | identical           | identical           | identical                       |

All 48 source × target × case combinations came back **identical**, nothing
was refused, every restored terminal re-encoded, and `ready()` gave the same
305-row renderable prefix in 0.4–7 ms on every build (the full table with
per-pair timings is what `bun run spikes/m3/cross-commit.ts` prints). The
snapshot's size did not change across the builds either, which says the
format was not touched in that window.

What this does and does not show: three distinct `tip` builds over 24 hours
of `main`, spanning one ABI addition, agree on format version 1 in both
directions. It is one window. A format-version bump upstream would presumably
show up as the decoder refusing (`ready()` throws a `GhosttyError`, which
the daemon logs and keeps the file for), not as a silent wrong screen — the
garbage-bytes test in M1 is the same path — but nothing here proves how
upstream will handle a bump, only that in this window there was nothing to
handle.

## A Bun finding: a pipe fd closed by hand kills a later socket

M2 recorded, as an open hypothesis, that a stalled `Bun.file(fd)` read on
the readiness pipe followed by `closeSync` "appears to break a later
`Bun.connect` client in the same process" (about one run in three, always
on the client's first request), and moved the fidelity scenarios out of
process to get around it. M3's tests hit the same shape three runs out of
three — a client whose `screen` request the daemon never answered, while the
daemon's own `stats` showed the connection had **hung up** and the client's
queue was empty and it had seen no `close` — and the restart-a-daemon
pattern made it reproducible enough to isolate. `spikes/m3/fd-reuse.ts`
spawns a child with a `"pipe"` on `stdio[3]`, handles the fd one of several
ways, then opens a Unix socket and forces a GC:

| After spawning with `stdio[3]: "pipe"`                                          | The socket opened afterwards |
| ------------------------------------------------------------------------------- | ---------------------------- |
| `Bun.file(fd).text()` then `fs.closeSync(fd)`                                   | **dies** once GC runs        |
| `fs.readSync` loop to EOF then `fs.closeSync(fd)`                               | **dies**                     |
| `fs.closeSync(fd)` without reading                                              | **dies**                     |
| `Bun.file(fd).text()`, never closed                                             | fine                         |
| `fs.readSync` loop, never closed                                                | fine                         |
| Never read, never closed                                                        | fine                         |
| `Bun.file(path)` / `fs.readFileSync` of the WASM, WASM compile, encode + decode | fine, any number of times    |

So it was never the read, and never the WASM: **Bun's `Subprocess` owns
the pipe fd and closes it again when the subprocess object is collected.**
Close it by hand first and the number is reused by the next socket, which
Bun's late close then shuts under its owner: the peer sees EOF, the socket's
own `close` handler never runs, and its next `write` returns 0. The WASM
loads in the tests only mattered by making a GC happen at the right moment.
The launcher now reads the readiness pipe with `fs.readSync` (EAGAIN → wait
5 ms → again) and never closes it; the M3 suite went from 6 failures to 11
passes on that one change, and the full suite has not flaked since. The M2
out-of-process arrangement for the fidelity scenarios probably no longer
needs to exist, but it costs nothing and was left alone. This is the sort of
thing worth a Bun issue once reduced to the spike, which it now is.

## M3 verdict

**Not hit.** The snapshot round-trips: every corpse's screen, cursor and
scrollback matched the record taken before the shutdown, and the same held
for a real `SIGTERM` to the detached process. The decoder's prefix is
renderable: `ready()` produced an attachable terminal with the viewport and
one page of history in a few milliseconds, before the rest of the history
was in, and the CLI paints it like any session. And adjacent `tip` commits
agree: three distinct builds across an ABI addition decoded each other's
snapshots in both directions with nothing to show for the difference. The
costs are small enough that the timer's design (encode every dirty session,
synchronously, every 30 s) needs no cleverness at this scale.

## What this implies for §3's fleet-agreement concern

It informs; it does not decide. The measurement says that within one day of
`tip`, and across one libghostty API addition, format version 1 was stable in
both directions — so a fleet whose daemons and browser bundles differ by a
few `tip` commits would probably have decoded each other's snapshots in that
window, and the plain-mismatch rule as built would have refused them anyway
because it compares commit SHAs, not formats. That looks stricter than
necessary: two of the four artifacts here were byte-identical under different
SHAs, and a rule keyed on the artifact's hash, or on the snapshot format
version the decoder actually checks, would have let those through. Whether
to loosen it is the open question: refusing on SHA is the cheapest rule that
can never be wrong, and the cost is that every werk release which bumps the
pin kills every corpse in the fleet unless something migrates them. The
evidence here suggests the format changes less often than the pin will, which
is an argument for keying the rule on the format (and letting the decoder's
own refusal be the mismatch signal) once someone has seen what an upstream
format bump actually looks like. Nobody has, and one window is not a trend.

## What M4 needs to know

**Getting a snapshot over the protocol.** `client.snapshot(id)` →
`{ id, engine, ghostty, cols, rows, bytes: Uint8Array, encodeMs }`; on the
wire it is `{ t: "snapshot", rid, id }` and a JSON reply with base64. A
corpse answers it too (its emulator is live even though nothing feeds it); a
mismatch corpse answers `no-snapshot`. The browser decodes with the same
two-stage `decodeState` the daemon uses — `ready()` for the first paint,
`next()` for history — and the reply's `ghostty` is what it should compare
against its own bundle's commit before trying. The `hello` handshake already
refuses a client on another pin, so in the PoC that check is redundant; in a
fleet it is the check.

**Live updates after the snapshot.** The `snapshot` reply is a point in time
and `output` frames keep flowing to an attached connection, so the browser's
sequence is attach (to start receiving output, and to be counted as a
client), then `snapshot`, then feed every `output` frame that arrives after
the reply into the decoded terminal. Output between the attach and the
snapshot is applied twice that way — once by the daemon before encoding, once
by the browser — which is wrong for anything but idempotent bytes. The clean
fix is for the daemon to encode the snapshot inside the attach and send it in
place of the `render` frame, so the byte stream starts exactly after the
state; that is a small change to `Session.attach` (a third frame type, or
`attach` gaining a `wants: "snapshot"` field) and is probably what M4 should
build rather than the two-request dance.

**Size.** `attach` still resizes a live session to the attacher's size, and
a corpse ignores the request; a browser tab decoding a snapshot gets the
emulator at the snapshot's size and should resize its own copy (the decoded
terminal reflows correctly, per M1) rather than expecting the daemon to.

**Snapshot sizes for the wire.** Plain sessions are tens of kilobytes;
heavily styled ones approach a megabyte (936 KB for 1,653 rows of per-cell
colour). Base64 in JSON adds a third; a binary frame would not. Encoding is
sub-millisecond either way.

**The state directory.** `$XDG_STATE_HOME/werk-poc/<id>.snap`, header line
then bytes. A web server inside the daemon would read the sessions, not the
files; one outside it would use `snapshot`. Nothing about the file is a
protocol.
