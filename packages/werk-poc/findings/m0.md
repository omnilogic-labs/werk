# M0 — smoke tests

What the proposal's §7 M0 list asks, what was run, and what happened. The
probes live in [`../spikes/m0/`](../spikes/m0/), one file per question, and
[`run-all.ts`](../spikes/m0/run-all.ts) runs each of them under each Bun
binary both interpreted (`bun run`) and as a `bun build --compile` binary.

## 1. `Bun.Terminal` inside a compiled binary

**Run.** `Bun.spawn(["sh", "-c", ...], { terminal: { cols: 80, rows: 24 } })`
where the shell prints `tty`, tests `[ -t 0 ]` and `[ -t 1 ]`, and prints
`stty size`.

**Result, all four cells.** The child reports `/dev/pts/N`, both stdin and
stdout are ttys, and `stty size` is `24 80`. `proc.stdout` is `null` and
`proc.terminal` is a `Terminal`, as documented. Nothing about the PTY layer
behaves differently in the compiled binary; `--compile` is not a factor in any
probe below either.

One thing a compiled probe does change: `process.execPath` is the compiled
binary itself, not `bun`. A daemon that re-invokes itself has to pass a role
argument rather than a script path (see `selfArgv` in `_lib.ts`). This bit the
first version of probe 2, which tried to run `process.execPath -e ...`.

## 2. Ctrl+C reaches the child as `SIGINT`

**Run.** Three children under a PTY, each sent a single `0x03` byte through
`terminal.write`:

- `bash` with `trap "echo GOT_SIGINT" INT`;
- a bare `sleep 30` with no handler;
- a Bun process with a `process.on("SIGINT")` handler (the probe re-invoking
  itself with a `child` role, so it works compiled).

The child's own `tty` output is compared with `ps -o tty=` for its pid.

**Result, all four cells.** The bash trap fires, `sleep` dies with
`proc.signalCode === "SIGINT"`, and the Bun child's handler runs. `ps` shows
the child with `tty pts/N`, `stat Ss+` (session leader, foreground process
group) and `sid == pgid == pid`. The PTY is the controlling terminal and the
child is in its foreground process group, which is the precondition for the
line discipline turning `0x03` into a signal at all.

The open Bun issue that says the PTY is not made the controlling terminal does
not reproduce on Linux with either version. It may be macOS-specific or fixed;
nothing here says which.

## 3. `SIGWINCH` on `resize()`, and `vim` redrawing

**Run.** `bash` with `trap 'echo WINCH:$(stty size)' WINCH`, resized
80×24 → 132×43 → 100×30. Then `vim -u NONE -i NONE -n` under an 80×24 PTY,
resized to 120×40 once the first screen is drawn.

**Result, all four cells.** The trap prints `WINCH:43 132` then
`WINCH:30 100`: the signal arrives and the new size is readable from the child.
After the resize `vim` emits a fresh screen — cursor-positioning and clear
sequences are present and the count of `~` filler rows goes from 22 to 38,
which only a 40-row redraw produces. Confirmed on 1.3.14 and 1.4.0 alike.

## 4. The `exit` callback's real contract

**Run.** Children that `exit 0`, `exit 3`, and a `sleep` killed with
`SIGTERM`. For each, count `exit` callback invocations before and after an
explicit `terminal.close()`, record the `(code, signal)` arguments, and note
whether the callback runs before `proc.exited` resolves. Plus a bare
`new Bun.Terminal()` closed with no child.

**Result.** This is the one place the two Bun versions differ.

| Observation                            | 1.3.14                       | 1.4.0                        |
| -------------------------------------- | ---------------------------- | ---------------------------- |
| Callback when the child exits          | once, `(1, null)`            | once, `(1, null)`            |
| Callback again on a later `close()`    | yes, `(0, null)` — two total | no — one total               |
| Bare `Terminal` with no child, `close` | once, `(0, null)`            | once, `(0, null)`            |
| Runs before `proc.exited` resolves     | yes                          | yes                          |
| `terminal.closed` after child exit     | `false`                      | `false`                      |
| `proc.exitCode` / `proc.signalCode`    | `0` / `3` / `SIGTERM`, right | `0` / `3` / `SIGTERM`, right |

The callback reports PTY lifecycle, exactly as the docs say: `1` means the
master read failed (`EIO` when the last slave closes), `0` means an orderly
close; `signal` is always `null`; the child's exit status never appears in it.
The "fires twice" the proposal mentions is real on 1.3.14 and is the
`EIO`-then-`close()` pair. 1.4.0 suppresses the second one.

For the daemon this means: the child's fate comes from `proc.exited` /
`proc.exitCode` / `proc.signalCode`, never from the terminal callback; the
callback is at most a hint that the PTY has gone quiet, and code that acts on
it must be idempotent because on 1.3.14 it will run again on `close()`. The
terminal does not close itself when the child exits; the daemon has to.

## 5. A PTY surviving the daemon being detached

**Run.** Four scenarios, each with a daemon started as
`Bun.spawn(self, { detached: true, stdio: ["ignore","ignore","ignore"] })`
plus `unref()`. The daemon holds a PTY running a shell that appends a line to
a file every 200 ms and also prints to the PTY, which the daemon relays to a
second file, so both the child and the `data` path are known alive.

1. The parent is an ordinary child of the probe and exits.
2. The parent runs inside a nested `Bun.Terminal`; the terminal is closed
   after it exits.
3. The parent runs under `script -qc`, which owns a PTY and tears it down
   when the parent exits.
4. The parent runs inside a nested `Bun.Terminal` and _stays alive_, attached,
   until that terminal is closed under it — the "laptop closes" case.

**Result, all four cells, all four scenarios.** The daemon has
`sid == pgid == pid`, `tty ?`, is re-parented to pid 776 (WSL's `/init`,
acting as the orphan reaper), and both files keep growing after the parent is
gone. In scenario 4 the parent receives `SIGHUP` when its PTY closes and
exits; the daemon receives nothing and its PTY child keeps running.
`detached: true` does call `setsid()` and that is sufficient; no double fork
and no `bun:ffi` involved, on either version.

## 6. A child that toggles raw mode

**Run.** `bash` that reads a line cooked, runs `stty raw -echo`, reads five
bytes raw, runs `stty sane`, reads another line. At each phase the probe
writes input and inspects the `data` callback, and reads the slave's termios
from outside with `stty -a -F /dev/pts/N` (the path comes from `ps -o tty=`
on the child). At the end it calls `terminal.setRawMode(true)` and `(false)`
itself and reads the termios again.

**Result, all four cells.**

- Cooked: the input is echoed back through `data` (`abc\r\n`) before the
  child's own output. Raw: nothing is echoed; only the child's `od` output
  arrives. Sane: echo returns. The daemon sees the effect of the child's
  termios in the byte stream and nothing else — the `data` callback carries no
  mode information and has no signature change.
- The mode _is_ detectable from outside: `stty -F` on the slave path reports
  `-icanon -echo -isig -opost` during the raw phase and the defaults otherwise.
  This works because the daemon owns the slave.
- `terminal.setRawMode(true)` from the daemon side clears `icanon`, `echo` and
  `isig` on the slave and leaves `opost` set; `setRawMode(false)` restores all
  three. It changes the child's termios, not something private to the master,
  so it is a way of forcing a mode on a child, not a way of observing one.

For werk this means "is the child in raw mode" is answerable, but only by
polling termios; there is no event. Whether that matters is a design question
for later — an emulator like libghostty does not need to know, and a CLI client
in pass-through mode always sets its own side raw regardless.

## 7. The latency floor

**Run.** A `cat` under a raw, no-echo PTY. One byte is written and the time
until it comes back is measured, 2,000 iterations, the first 10 % dropped as
warm-up. Three paths:

- **PTY only**: `terminal.write` → `data` callback, in-process.
- **Bun relay**: a Unix-socket client (`Bun.connect`) → `Bun.listen` server →
  `terminal.write` → `data` → `socket.write` → client. This is the daemon's
  actual job.
- **socat**: `socat UNIX-LISTEN:… EXEC:cat,pty,raw,echo=0` doing the same
  relay natively, measured by the same Bun client.

`dtach` is not installed and no system packages were added, so the comparison
the proposal names is not taken here; `socat` stands in as a rough native
floor.

**Result** (microseconds, round trip; two runs each, the spread between runs
is a few µs at p50 and tens at p99):

| Path      | 1.3.14 p50 | 1.3.14 p99 | 1.4.0 p50 | 1.4.0 p99 |
| --------- | ---------- | ---------- | --------- | --------- |
| PTY only  | 61–66      | 125–198    | 78–81     | 145–158   |
| Bun relay | 65–67      | 147–218    | 86–91     | 160–185   |
| socat     | 94–96      | 194–230    | 95–103    | 163–204   |

Interpreted and compiled numbers are indistinguishable. Adding the socket hop
costs about 4–8 µs at p50 over the bare PTY round trip. The Bun relay is
faster than `socat` at p50 on this machine, which says more about `socat`'s
buffering than about Bun, and the p99s overlap. 1.4.0 is consistently ~20 µs
slower than 1.3.14 at p50 on the PTY path across both runs; small, but
consistent enough to be worth re-measuring on a non-WSL kernel before drawing
a conclusion from it. Either way the relay floor is well under a millisecond,
and latency in this path is not the constraint on the design.

## Differences between 1.3.14 and 1.4.0

- The `exit` callback fires once on 1.4.0 (PTY `EIO` only) and twice on
  1.3.14 (`EIO`, then again on `close()`). Everything else in probe 4 agrees.
- Round-trip latency is ~20 µs higher at p50 on 1.4.0.
- Compiled binaries are 12 MB smaller on 1.4.0.
- Nothing else differs in any probe.

## Verdict

M0's stop condition — "`Bun.Terminal` does not work compiled, or cannot deliver
`SIGINT`, or cannot deliver `SIGWINCH`" — is **not hit**. `Bun.Terminal` works
identically interpreted and compiled on both Bun versions; `0x03` delivers
`SIGINT` because the PTY is the child's controlling terminal; `resize()`
delivers `SIGWINCH` with the new size and `vim` redraws to it; a detached
daemon and its PTY survive the parent and the parent's terminal going away.
Nothing found here changes §4's shape. The two things downstream work has to
carry are that the `exit` callback is not the child's exit signal and may fire
twice, and that a compiled binary re-invokes itself by role rather than by
script path.

Everything here is one machine, one kernel, and WSL2 at that. macOS is not
covered, and the controlling-terminal issue the proposal cites may be a macOS
one.
