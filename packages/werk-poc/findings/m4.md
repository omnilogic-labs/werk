# M4 — `wp serve`: the browser runs the daemon's emulator

What the proposal's §7 M4 row asks: `wp serve` with a session list and one
live terminal driven by state transfer plus per-consumer dirty rows, keys
and mouse through the WASM encoders, rendered by `ghostty-web` rebased onto
the pinned artifact. The stop condition has two halves: "the browser cannot
decode what the daemon encodes, or the renderer route costs more than the
rest of the PoC combined". This file covers both halves. The first is the
daemon side, the web server, the page and a deliberately minimal renderer
written to prove the round trip and to be measured. The second is
[the renderer route](#the-renderer-route-four-renderers-behind-one-interface):
four renderers behind one interface, fed the same `Frame`s and chosen by
`?renderer=` on the terminal page — the minimal one, `ghostty-web` rebased
onto the seam, and adapters onto two published renderers, `@wterm/dom` and
`@beamterm/renderer` — so that one session can be measured through each in
turn. The verdict on both halves is [at the end](#m4-verdict).

**The first half of the stop condition is not hit.** The browser decodes
what the daemon encodes: the same `ghostty-vt-small.wasm` bytes, served by
the daemon's own process, instantiated in Chrome, fed the daemon's
`GHOSTSNP` snapshot and then the raw output after it, hold a replica whose
viewport text is byte-identical to the daemon's `screen` after `vim`, after
keys typed through the page, after a resize, after a lag and resume, in
two tabs at once, and on a corpse. The evidence is in
[the browser run](#the-browser-run) and the tests.

The code is under [`../src/web/`](../src/web): `server.ts`, `pages.ts`,
`wire.ts`, `build.ts`, and the page under `client/`. The daemon changes are
in `protocol/index.ts`, `daemon/session.ts`, `daemon/connection.ts`,
`daemon/server.ts` and `client/index.ts`. `bun test` is 176 across 23
files in about 50 s (the vendored `ghostty-web` clone carries a suite of
its own, which `bunfig.toml` keeps out), and no daemon, `wp serve` or
browser is left behind.

## The design as built

**Snapshot on attach.** `attach` gained `mode: "vt" | "snapshot"`. In
snapshot mode `Session.attach` encodes the emulator inside the attach and
sends the bytes as a new frame type, `snapshot` (4), in place of `render`;
the lag → resume path sends a fresh `snapshot` the same way, through one
`Session.paint(mode)` that the attach, the resume and a new `repaint`
request all use. The ordering that makes a replica exact rather than
approximately right is by construction: `attach` registers the client,
encodes, and enqueues the frame in one synchronous step, and the PTY's
`data` callback cannot run in the middle of it, so every `output` frame
after the snapshot carries bytes the emulator consumed after the encode.
The two-request dance M3 warned about (attach, then `snapshot`, with the
output in between applied twice) is gone. `Session.encode()` is the read;
`snapshot()` is the checkpoint that clears `dirty`, and the `snapshot`
request now uses the read, which its comment had claimed all along.
Corpses take the same path: a restored corpse's emulator encodes, a
mismatch corpse has nothing to encode and sends its placeholder as a
`notice` with no frame. The CLI stays on `vt`.

**`wp serve`.** `Bun.serve` on `127.0.0.1`, port 0 by default (`--port` to
fix), printing a URL with a one-time token in the query string. The first
request carrying the token gets a `302` to the same path and an `HttpOnly;
SameSite=Strict` cookie; every other request, the WebSocket upgrade
included, needs the cookie or gets `403`. `GET /` is the session list from
`ls`, server-rendered, with a two-second refresh of the table body from
`/api/ls`; `GET /s/:id` is the terminal page; `GET /app.js` the bundle;
`GET /wasm` the pinned bytes with `application/wasm`, read from the same
embedded path the daemon loads, so the compiled binary serves them with
nothing on disk. `WS /ws/:id?cols=&rows=` is one connection to the daemon
and one snapshot-mode attach per socket. Server to page: binary messages
tagged with a first byte (0 output, 1 snapshot) and JSON notices (`hello`,
`exited`, `lagging`, `resumed`, `notice`, `effect`, `error`). Page to
server: binary is input for the PTY, JSON is `{t:"resize"}`. `/api/ws`
reports each socket's backpressure accounting.

**The page.** Fetches `/wasm`, instantiates it through the same
`GhosttyWasmEngine.load` the daemon uses, measures its cell size off a
canvas, computes the grid from the container, opens the socket at that
size. A `Replica` (`client/replica.ts`, no DOM) owns the terminal: on a
snapshot it disposes the old terminal, runs `decodeState` and `ready()`,
takes one render consumer, paints its first frame synchronously, and then
pulls `next()` pages one per `setTimeout(0)` so the first paint is
presented before history finishes; live output is written into the
terminal and a paint is coalesced through `requestAnimationFrame`. Keys go
`keydown` → `keyEventFromDom` (the W3C `code`, the `key` as the text, the
modifiers) → `engine.encodeKey(ev, replica.modes())` → the socket; mouse
the same way through `encodeMouse`, only while the replica's modes report
a tracking mode. Paste is the one extra: the `paste` event sends the text,
bracketed when DEC 2004 is on. Resize measures the container, resizes the
replica locally (the decoded terminal reflows exactly as the daemon's
does, findings/m1.md) and tells the daemon. The status line shows the
decode timings, the paint costs and the lag state; a bell flashes the
background. Everything measured is on `window.__wp`.

**The renderers** sit behind one small interface in `client/renderer.ts`,
so the page can be measured through any of them without changing;
[the seam](#the-seam) has the shape. `?renderer=` picks one at load and the
minimal one is the default.

`CanvasRenderer` is that minimal one: a monospace grid on one canvas, and
for each changed row it clears the row, fills non-default backgrounds (inverse swaps), draws
each cell's text with bold/italic through the font string, underline and
strikethrough as one-pixel lines, wide cells across two columns with the
spacer skipped, and the cursor in its four styles over the cell, keeping a
shadow copy of painted rows so the row the cursor left can be repainted.
xterm's sixteen colours, the cube and the grey ramp computed on demand.
That is all it is; the list of what it does not do is
[below](#what-the-minimal-renderer-does-not-do).

**The bundle.** `bun run build:web` runs `Bun.build` with
`target: "browser"` on `client/main.ts` and writes `src/web/bundle/app.js`
(238,077 B unminified, all four renderers in it); `server.ts` imports that
file `with { type: "text" }`, which `bun build --compile` embeds like the
wasm, so `bun run build` runs the bundle first and the compiled `wp`
carries it. The built file is gitignored; `bundle/app.d.ts` lets tsc
resolve the import without it, and `server.test.ts` builds it if it is
missing. beamterm's 1.4 MB of WebAssembly is not in the bundle: it is
embedded in the binary separately and served from `/beamterm.wasm`, which
only the beamterm renderer fetches.

The bundle is loaded as `<script type="module">`, and it has to be —
[the module-script trap](#the-module-script-trap) is what happens when it
is not.

## The Bun-free loader, confirmed

`loader.ts`, `layout.ts`, `index.ts` and `encoders.ts` bundle for the
browser as they are; `bytes.ts` stays the only Bun file and the page
replaces it with `fetch("/wasm")`. The bundle has no `Bun.`, `bun:`,
`process.` or `Buffer` reference (a test greps for the first two). The
one change the browser needed was a type, not code: under the DOM lib
`WebAssembly.compile` wants a `BufferSource` whose `Uint8Array` generic
differs from Bun's, so `GhosttyModule.load` casts the bytes to
`ArrayBuffer | Uint8Array<ArrayBuffer>`, which both libs accept. The
browser files have a `tsconfig.json` of their own with `lib: [dom]` and
`types: []`, no `bun-types` at all, and `bun run typecheck` runs both
configurations; that is the type-level proof that nothing in the page
reaches for Bun. The trampoline for host functions (M1's `hostFunction`)
is not exercised in the page because a replica subscribes to no effects —
the daemon's emulator is the one that answers queries — so whether
`new WebAssembly.Module` of a forty-byte module is allowed synchronously
on Chrome's main thread remains unmeasured here; M1's note says it should
be.

Loading in Chrome: 721 KiB of wasm fetched and instantiated in 6–12 ms
(warm cache; the status line reports it), which is below the time the
first snapshot takes to arrive.

## Bun's WebSocket backpressure API, and the rule built on it

What Bun 1.3.14 gives a `ServerWebSocket`, from its types and docs:

| Item                       | What it is                                                                                                                                                            |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ws.send(data)` return     | `-1`: enqueued, but there is backpressure. `0`: dropped because of a connection issue. `1+`: bytes sent. (`sendBinary`/`sendText` the same.)                          |
| `drain(ws)` handler        | Fires when the enqueued bytes are gone                                                                                                                                |
| `backpressureLimit` option | How much Bun will hold for a socket, default 16 MiB; `closeOnBackpressureLimit` (default false) closes the socket past it, otherwise sends past it return `0`         |
| `bufferedAmount`           | **Not on the server socket.** It exists on Bun's client `WebSocket`, not on `ServerWebSocket`, so there is no way to read how much is queued between `-1` and `drain` |

So the rule is the simplest one that never needs `bufferedAmount`: the
first `-1` marks the socket lagging and starts a timer; while lagging,
output frames are dropped for that socket and counted; on `drain` the
server asks the daemon to `repaint`, keeps dropping until the snapshot
frame arrives in the daemon's stream (so nothing consumed before the
encode is forwarded), sends it, and forwards output again. The user-space
bound is therefore zero bytes on top of what the kernel and the browser
accept, which is a different shape from the daemon's 256 KiB queue over
the kernel's buffer; measured, that turned out generous enough (2.9 MB
before the first `-1`, below). `backpressureLimit` is set to 4 MiB so a
snapshot enqueued under backpressure is never the message Bun drops; in
the run, `droppedByBun` stayed 0. Two stages, one page: the daemon's
socket to the web server lags and resumes on its own with a snapshot the
server forwards; the WebSocket lags and resumes with a snapshot the
server asked for. The page shows which (`lagging (daemon)` /
`lagging (ws)`).

The measurement: `yes | head -c 40000000` (60 MB after the line
discipline's CRLF) into a page whose next message handler busy-looped for
5 s (`window.__wp.stall(5000)`, so the tab stopped draining its socket):

| Quantity                                        | Value                                                                                                                                  |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `ws.send` calls                                 | 4,415; two returned `-1`, none `0`                                                                                                     |
| First `-1` after                                | **2,897,200 B** accepted by the kernel and Chrome                                                                                      |
| Lag episodes / drains                           | 1 / 1                                                                                                                                  |
| First `-1` to `drain`                           | **907 ms**                                                                                                                             |
| Output dropped for the socket                   | 7,612,845 B                                                                                                                            |
| Bytes sent over the socket                      | 52,402,146                                                                                                                             |
| Snapshots sent                                  | 2: the attach's and the resume's                                                                                                       |
| The page                                        | one `lagging (ws)`, one `resumed (ws)`, both delivered together once the stall ended; text identical to the daemon's screen afterwards |
| Daemon-side lag on the socket to the web server | none                                                                                                                                   |

The drain came 907 ms into a 5 s stall, which says the browser's network
process kept reading the socket into its own buffer while the renderer
was blocked — Chrome absorbs a lot before TCP backpressure reaches Bun,
and once it does, Bun's `-1` and `drain` are prompt. The 2.9 MB absorbed
before the first `-1` is the loopback kernel buffers plus that; on a real
network it would be smaller.

## A bound the first half found in M2's rule

Opening the heavily styled session (a 1,053,913-byte snapshot, below) put
the daemon's connection to the web server into lag on the next 20 bytes
of output and earned it another megabyte on the drain:

```
conn 31: short write on a control frame (219264 of 1053918), 834654 B queued, waiting for drain
conn 31: lagging, dropped 20 bytes, 323160 control bytes still queued
conn 31: resumed with a 1053913-byte snapshot
```

The daemon's queue bound was measured against everything queued,
non-droppable paints included, so a paint larger than the bound made the
connection lag on the first droppable frame after it, and each drain
produced another paint — a loop for as long as output kept coming. The
bound now applies to the droppable bytes alone (`queuedDroppable` in
`connection.ts`); memory stays bounded because the non-droppable part is
one paint plus control messages. M2's slow-client numbers are unchanged
by it (max queue 260,973 B under the 262,144 B bound on the re-run).
Whether a product wants the bound expressed as bytes over the paint, as
time, or both, is the question M2 already left open.

One caveat about how keys were sent. `agent-browser`'s `keyboard type`

so letters, digits, Enter, Escape, Backspace and Space went through

and `!` were dispatched as `KeyboardEvent`s carrying the `key` Chrome
would have produced. Both routes end in the same handler and the same
encoder call; the tool, not the page, is what could not produce a `:`.

The paint numbers measure what the page's JavaScript spends issuing canvas
commands; Chrome rasterises them off the main thread afterwards, so they
are a floor for the cost of the renderer, not the cost of pixels reaching
the screen. That is the right number for "does the page keep up with
output" and the wrong one for "how heavy is this renderer". The same limit
applies to every renderer measured [below](#the-four-side-by-side), and it
bites hardest on the DOM renderer, where the work the browser does after
the JavaScript returns is style and layout rather than rasterising a
canvas.

## What the minimal renderer does not do

This is the list the other three are priced against, in the order a user
would notice. None of it is a fault: the minimal renderer exists to prove
the round trip and to be the floor the others are measured from.

- **Selection.** Nothing is selectable: the canvas has no text, so the
  browser's native selection does not apply, and no selection of the
  grid's own is built. `window.__wp.select()` returns null under it, and
  copy is absent too.
- **Scrollback scrolling.** The viewport is painted wherever the replica
  puts it, so `window.__wp.scroll()` moves it under this renderer as it
  does under the others; what is missing is a way for a user to ask. The
  wheel is sent to the program only when a mouse mode is on and does
  nothing otherwise, because the page wires the wheel to viewport
  scrolling only for a renderer that brings a selection.
  `frame().viewport` carries the scrollbar shape, so the data is there.
- **Fonts and graphemes.** One font string, `14px monospace`; a cell's
  text is whatever `fillText` makes of it, clipped to its column width.
  No fallback fonts, no ligature handling, no grapheme-width correction
  beyond the wide/spacer cells libghostty reports, no box-drawing or
  Powerline glyph special-casing. Emoji drew, at the system's mercy.
- **IME and composition.** `keydown` with `isComposing` is ignored and
  nothing is composed anywhere; there is no hidden input element.
- **Links.** `hyperlink` on a cell is not read; nothing is clickable.
- **Cursor blink** is not animated; the style and visibility are drawn
  from `frame().cursor`.
- **Faint, blink, double underline, underline colour, undercurl** are
  not drawn; `Cell` does not carry the last three yet.
- **Device pixel ratio** is applied to the canvas, but the cell size is
  measured in CSS pixels and rounded up, so fractional metrics drift.
- **Focus** is document-wide keyboard capture; there is no focus ring and
  no way to give a key to the browser except Ctrl+Shift+V and F12.
- **Bell** is a background flash; no sound, no title marker.
- **Resize** is a whole repaint with no debounce.
- **Accessibility**: nothing — no text in the DOM, no live region.

## M4, first half: verdict

**Not hit.** The browser decodes what the daemon encodes, and does so with
the two-stage split the proposal wanted: on a 5,000-line session the page
painted 1.0 ms after the snapshot arrived, with 1,080 rows still pending,
and had them 1.7 ms later. Everything in the §7 row except the renderer
is built — the list, the live terminal driven by state transfer and
per-consumer dirty rows, keys and mouse through the WASM encoders — and
the minimal renderer sits behind an interface small enough that three
others sit behind it too. What that interface costs to fill, against the
rest of the PoC, is the second half, below.

## The renderer route: four renderers behind one interface

The proposal's §3 picks the rebase of `ghostty-web` onto the pinned
upstream artifact as the PoC's renderer route, with re-emission into
xterm.js as the fallback, and asks for one piece of evidence: how much of
ghostty-web's renderer survives a rebase, and how much of it would be
worth keeping. That question is answered [below](#ghostty-web-rebased),
and answering it made the seam wide enough that the question can be put to
a published renderer as well. So there are four behind it:

| `?renderer=`  | What it is                                                      | Draws     |
| ------------- | --------------------------------------------------------------- | --------- |
| `minimal`     | `CanvasRenderer` in `client/renderer.ts`, the default           | Canvas 2D |
| `ghostty-web` | ghostty-web's renderer and selection rebased onto `Frame`       | Canvas 2D |
| `wterm`       | `@wterm/dom` 0.4.1 driven through a `TerminalCore` over `Frame` | DOM rows  |
| `beamterm`    | `@beamterm/renderer` 1.0.0 fed cell by cell from `Frame`        | WebGL2    |

All four take the same `Frame`s from the same `Replica` and are chosen at
load, so one session can be measured through each in turn; that
measurement is [further down](#the-four-side-by-side). Two of them draw a
canvas, one draws DOM rows and one draws WebGL2, which is the spread the
comparison is for.

### The seam

- The interface is `Renderer` in `client/renderer.ts`: `paint(frame)`,
  `resizeTo(cols, rows)`, `dispose()`, `cell`, `stats`, and two optional
  members — `surface`, the element that takes focus, keys and mouse when
  it is not the canvas, and `selection`, non-null when the renderer brings
  a selection of its own. `main.ts` mounts one at load, reads `cell` to
  compute the grid and to convert mouse pixels to cells, calls `resizeTo`
  before the first paint, and calls `paint` with every `Frame` the
  `Replica` produces (the first synchronously after `ready()`, the rest
  through `requestAnimationFrame`).
- What a renderer is offered at construction is a `RendererHost`, and
  `RendererFactory` is `(host) => Promise<Renderer>`, async because one of
  them fetches a WASM module first. The host carries the mount element,
  the canvas the page ships with, `requestPaint`, and the things a
  selection asks the page for: `viewportOffset`, `cols`, `rows`,
  `textBetween`, `scrollLines` and `selectionEnabled`. The two canvas
  renderers take only the canvas out of it; the host is that wide because
  a renderer that owns its own selection has to ask the page for exactly
  what a selection controller would.
- `RendererSelection` is the shape `window.__wp` exposes, so a harness
  reads the same surface whichever renderer is mounted: `getSelection`,
  `hasSelection`, `clearSelection`, `selectViewport`, `viewportChanged`,
  `lastCopied`. ghostty-web's `SelectionController` satisfies it
  structurally; wterm and beamterm each supply their own.
- The renderers share `newPaintStats`, `recordPaint`, `palette` and
  `cssColor` from the same file, so every renderer reports its cost in the
  same shape and resolves an indexed colour the same way.
- `MouseEvent.offsetX` is relative to the event's target, which is the
  canvas for a canvas renderer and a row element for a DOM one, so a DOM
  renderer's mouse pixels come out per row rather than per grid.
  `client/input.ts` takes an optional `SurfaceOrigin` and re-bases the
  pixels on the surface; the page caches that origin and refreshes it on
  resize rather than measuring on every event.
- A `Frame` is the seam's: `changed` rows with `Cell`s (`text`, `fg`,
  `bg`, bold/italic/underline/inverse/strikethrough, `width` 0/1/2),
  `dirtyAll`, the `cursor` and `cursorChanged`, the `viewport`. A renderer
  that wants raw packed `GhosttyCell`s or the render state handle would
  have to reach past the seam into `GhosttyWasmTerminal`; `Replica.term`
  is that terminal.
- The page's structure is one file, `client/main.ts`: `state` and
  `renderStatus()`; `onMessage` splitting tagged binary from JSON;
  `Replica` for decode and output; `applySize` for resize; the input
  handlers at the bottom of the file; `window.__wp` for measurement.
  `client/input.ts` is the DOM-to-seam mapping and stays whatever the
  renderer is; `client/replica.ts` is DOM-free and tested under Bun.
- Two tabs each hold a `Replica` and a consumer of their own; the daemon
  holds one emulator and sends each socket its own snapshot. A renderer
  that keeps state across frames — and all four keep shadow rows — is per
  tab by construction.
- What no renderer may change is the frame path, because the daemon's
  snapshot and the browser's live output are the same bytes and the same
  code, and a renderer that re-emits VT into a second emulator gives that
  up (proposal §3).
- The page attaches at its own grid and resizes the session; the CLI's
  size rule ("most recent attacher wins", M2) applies to browser tabs
  unchanged and is still a product question. Each renderer derives its own
  cell box from its own font metrics, so the same window gives each of
  them a different grid.

## `ghostty-web`, rebased

The clone is described in [`../vendor/README.md`](../vendor/README.md)
(commit `1858a594…`, the default branch on 2026-06-28, release 0.4.0,
MIT); the port is `client/renderer-ghostty-web.ts` and

### What ghostty-web is

A browser terminal with an xterm.js-shaped API over Ghostty's VT parser,
built from a Ghostty submodule pinned in December 2025 plus a 1,620-line
patch (`patches/ghostty-wasm-api.patch`) that adds its own
`include/ghostty/vt/terminal.h` and the Zig behind it. The patch's API is
the shape of the whole library: `ghostty_terminal_new(cols, rows)`,
`ghostty_render_state_update` returning a dirty enum, one
`ghostty_render_state_get_viewport` call filling a packed buffer of
`GhosttyCell`s (a codepoint, foreground and background **already resolved
to RGB** inside the WASM, a flags byte, a width, a hyperlink id, a
grapheme count), per-row dirty flags, `ghostty_terminal_get_scrollback_line`
and `_length`, `_get_hyperlink_uri`, `_is_alternate_screen`, `_get_mode`,
and the key encoder. None of it is upstream's `terminal.h`; upstream's
render state, selection, formatter and scroll API do the same jobs with a
different shape and, for selection and scrolling, do more.

### How the rebase was done

The `Frame` from the seam is a different shape from `IRenderable`: it
carries the rows that changed rather than answering `getLine(y)` for any
row, its rows are already whatever the viewport shows (libghostty scrolls
the viewport itself; a scrolled frame is `dirtyAll` with the new rows),
its colours are the seam's `Color` rather than resolved RGB, a cell's text
is the whole grapheme, and the cursor's shape is the terminal's. So the
port keeps a shadow copy of the rows as painted — ghostty-web's
`getLine` answered from that — and re-targets each area:

## `wterm`: DOM rows from `@wterm/dom`

`@wterm/dom` 0.4.1 is Apache-2.0, published by Vercel Labs on 2 September 2026. It is worth measuring because it paints real DOM rows rather than a
canvas: selection, copy, the browser's own find and whatever
accessibility the DOM affords come from the browser instead of from a
controller the page has to write. What that costs at werk's output rates
is exactly what is not known.

`client/renderer-wterm.ts` does not use the package's `WTerm`
orchestrator, which owns WASM loading, input, resize observation and a
render loop of its own — all of which the page already has. It drives the
bare `Renderer` class through a hand-written `TerminalCore` adapter over
`Frame`. That is the interface's own invitation: `@wterm/core`'s doc
comment says alternative backends implement `TerminalCore` "so that
`@wterm/dom` can render any core interchangeably". So werk supplies a
shadow grid rather than an emulator. `paint(frame)` converts the rows
`frame.changed` names into wterm's `CellData` and marks them dirty, and
`Renderer.render` pulls them back through `getCell`/`isDirtyRow`, so a
one-row frame rebuilds one row of DOM and nothing else; everything an
emulator-driving core would answer — writes, resizes, responses — is a
stub.

The cell encoding is documented nowhere, so it was read out of the shipped
code:

| Field           | What it is                                                                                                                                                                                          |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `flags`         | A bitfield in SGR order: bold `0x01`, dim `0x02`, italic `0x04`, underline `0x08`, blink `0x10`, reverse `0x20`, invisible `0x40`, strikethrough `0x80`                                             |
| `fg` / `bg`     | Palette indices, `DEFAULT_COLOR = 256` meaning the default. `wasm-bridge.js` reads a cell as `char u32, fg u16, bg u16, flags u8, width u8, link u16`, so 256 fits and nothing larger is meaningful |
| `fgRgb`/`bgRgb` | Packed `0xRRGGBB`, taking priority over the index. wterm's own core never sets them; this adapter sets them for a truecolour cell only                                                              |
| `width`         | werk's meaning unchanged: 0 is the continuation of the wide cell to its left                                                                                                                        |

Two things are deliberately unused. wterm's virtualised scrollback is off
— `getScrollbackCount()` reports 0 and `render()` is called with no
`RenderViewport` — because libghostty owns the viewport and running both
would scroll twice. And the selection is the browser's own native
selection, re-anchored by absolute row so that it follows a scroll rather
than staying on the DOM rows it started on.

The limitations, plainly:

- The 256-colour cube (indices 16–231) resolves through wterm's own cube,
  which steps by 51 where werk's palette steps 0/95/135/175/215/255, so
  those cells do not match the canvas renderers pixel for pixel. The
  sixteen ANSI slots do match, because the page binds
  `--term-color-0…15` to werk's palette.
- wterm paints block elements U+2580–U+259F as an empty span with a
  background, so those glyphs are absent from the DOM and from any text
  copied out of it.
- Soft-wrapped rows copy as separate lines, because the DOM records no
  wrap where libghostty's formatter rejoins them. Copying a wrapped line
  from wterm and from the other three gives different text.
- The stylesheet is a subset of `@wterm/dom/src/terminal.css` inlined into
  the adapter, because a `with { type: "text" }` import of it is rejected
  by `tsc` here.

It adds about 52.6 KB to the browser bundle. `WTerm`, `InputHandler`,
`DebugAdapter`, `WasmBridge` and wterm's own inline WASM all tree-shake
out, so none of its emulator is carried.

## `beamterm`: WebGL2 from `@beamterm/renderer`

`@beamterm/renderer` 1.0.0 is MIT, one maintainer, compiled from Rust to
WebAssembly and drawing WebGL2. It is explicitly a renderer and not an
emulator: cells go in through `batch().cell(x, y, data)` and `render()`
draws them, while parsing, grapheme segmentation, the cursor and the
scrollback belong to whoever feeds it. That suits this seam, because
libghostty has done all of that by the time a `Frame` arrives.

`client/renderer-beamterm.ts` establishes the encodings by running the
package's Node build and by reading the shader out of the binary, rather
than by guessing:

- `fg` and `bg` are 24-bit `0xRRGGBB` with no alpha; a colour set on a
  cell comes back unchanged.
- The style bits sit above a packed glyph index: bold `0x400`, italic
  `0x800`, underline `0x2000`, strikethrough `0x4000`. The fragment shader
  takes the emoji bit as a _uniform_ — `u_emoji_bit`, 12 for a static
  atlas and 15 for a dynamic one — which is how the public bits stay
  stable whichever atlas is mounted. The adapter still builds its style
  table at runtime by asking the shipped `CellStyle` builder for each of
  the sixteen combinations, so the numbers come from the package rather
  than from a reading of the shader.
- wasm-bindgen objects are not garbage collected, so ownership is by hand.
  One `Cell` is reused and mutated across a whole paint — the generated JS
  shows the setters mutating in place and `Batch.cell` borrowing rather
  than consuming — and `Batch`, `Size`, `TerminalSize`, `ModifierKeys`,
  `CellQuery`, `UrlMatch` and the handler's `MouseEvent` are each freed
  explicitly.

**The atlas is the substantial finding.** The embedded static atlas's
symbol table was parsed straight out of `beamterm_renderer_bg.wasm`, as
length-prefixed UTF-8 records from offset 346406: **4084 glyph slots,
being 1021 characters in four style variants**. They cover ASCII, Latin-1
and Latin Extended, Greek and Cyrillic, box drawing, block elements,
braille, geometric shapes, dingbats and astral emoji. They contain **no
CJK ideograph, no kana and no hangul at all** — those characters are
absent from the whole 1.39 MB binary as UTF-8 byte sequences, as are `→`
(U+2192) and `★` (U+2605). With that atlas, `日本語` rendered as nothing:
no glyphs, no placeholder boxes, and no error from WebGL2.

So the adapter asks for `withDynamicAtlas(["monospace"], 14)`, which
rasterises glyphs on demand through the browser's canvas API, and writes
wide graphemes through beamterm's width-aware `batch.text` rather than a
per-cell write, so beamterm places whatever the spacer column needs.
Asking for 14 px monospace also brings its grid into line with the other
three, which is what makes them comparable in one window. Three things
follow that this run does not settle:

- The first paint that brings a new glyph into view pays to rasterise and
  upload it, so a paint that scrolls new script into view presumably costs
  more than one that does not.
- The atlas has a finite number of slots and the package documents no
  behaviour at the limit, so what a session showing enough distinct glyphs
  does is unknown.
- Coverage is now the browser's `monospace` fallback rather than the
  embedded atlas, so a machine with no CJK-capable font would fail
  differently: tofu rather than nothing.

**What it costs.** 1,385,793 bytes of WebAssembly, fetched from
`/beamterm.wasm` only when this renderer is chosen, so nothing else pays
for it; about 76 KB of JavaScript glue is in the bundle whether it is
chosen or not. It embeds its own font atlas and does its own Unicode work,
most of which goes unused because libghostty has already segmented the
cells — and with a dynamic atlas the embedded static atlas is carried and
never sampled, which sharpens that trade rather than softening it.

`TerminalDebugApi` would report the atlas's glyph count and the glyphs a
session asked for and did not get, which is exactly what a coverage
question wants. `getMissingGlyphs`, `getGlyphCount` and the string
`Terminal debugging API exposed at window.__beamterm_debug` are compiled
into the WASM, but nothing in the shipped type definitions reaches it and
the log does not appear in a run, so it looks to sit behind a build
feature this package does not ship.

**Selection** is beamterm's own: modifier-aware selection, clipboard
handling and `findUrlAt` for link hit-testing.
`enableSelectionWithOptions` fixes the required modifier at the moment it
is called, and werk's rule depends on live mouse-tracking state, so the
adapter re-arms it whenever the answer flips. beamterm exposes no way to
read the current selection back as a `CellQuery` and no way to _set_ one,
so the adapter observes the drag through `setMouseHandler` and
reconstructs the range in absolute rows; a selection made programmatically
therefore produces text but no highlight. `findUrlAt` is exposed on the
adapter as `urlAt(col, row)`, and the page does not call it yet.

## The four, side by side

One run, Chrome, the compiled `wp`, one window: a live session printing
bold red, italic green and underline, a 256-colour background block, a
truecolour word, `日本語` and `┌─┐`, then forty numbered lines, opened
through each `?renderer=` in turn.

All four reach `running`, with no console errors and no uncaught
exceptions. All four render the text, the bold, the italic, the underline,
the 256-colour block, the truecolour word, the CJK at double width without
overlapping the text after it, and the box-drawing characters. A cursor is
visible in all four. The box-drawing check here is a single-row `┌─┐` and
it draws under `ghostty-web` too, where the multi-row box above loses its
horizontals; the two checks are not the same shape and why one survives
and the other does not has not been chased.

`window.__wp.repaint()` — one forced full repaint, in milliseconds — on
the same window and the same session:

| Renderer      | Grid   | Repaint (ms)                |
| ------------- | ------ | --------------------------- |
| `minimal`     | 142×30 | 0.7 / 0.6 / 0.5             |
| `ghostty-web` | 142×36 | 1.6 / 1.3 / 1.4             |
| `wterm`       | 151×32 | 1.4 / 0.7 / 0.7             |
| `beamterm`    | 142×32 | 1.3 / 0.9 / 0.6 / 0.4 / 0.4 |

Read those for what they are: a handful of forced full repaints, on one
machine, in one browser, on one session, with nothing running. They are
not a benchmark and there is no winner in them. The grids differ because
each renderer derives its own cell box from its own font metrics, so the
four are not even painting the same number of cells. beamterm's first
repaints being the slowest and then settling is consistent with
on-demand glyph rasterisation on first touch, which is a reading and not a
measurement.

The question the four exist to answer is whether DOM rows hold up at
werk's real output rates — under a noisy build, not a static screen — and
this does not answer it. A forced repaint of a still screen measures one
whole-grid rebuild with nothing competing for the main thread, which is
not the shape of a build scrolling a viewport a frame at a time. That
question is open.

Selection and scrolling:

| Check                                                   | Result                                                                                                                                             |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `window.__wp.select(0, 0, 30, 0)`                       | Returns the row's text on `ghostty-web`, `wterm` and `beamterm`, and `selection()` and `lastCopied()` agree with it                                |
| The same on `minimal`                                   | `null`: the minimal renderer has no selection, which is a property of it and not a fault                                                           |

## The module-script trap

The page bundle is loaded as `<script type="module">`, and it has to be.
beamterm's wasm-bindgen glue contains
`new URL("beamterm_renderer_bg.wasm", import.meta.url)` on a fallback
branch that never executes, because the adapter always passes the module
explicitly. But `import.meta` is a _parse-time_ error in a classic script,
so with a plain `<script src>` the whole bundle failed to parse and all
four renderers were dead at once: the page stuck at "loading…" with
`window.__wp` undefined. Both `tsc` and `Bun.build` passed the same file
without complaint, because neither of them knows how the page will load
it. Nothing but opening the page catches that, which is an argument for
opening the page.

## Speculation for after the PoC

The proposal's §8 row reads "rebasing `ghostty-web` costs more than
writing a renderer → the renderer is werk's own from the start". The
measurement does not fall cleanly on either side of that row, because
"rebasing ghostty-web" turned out not to be an integration at all: what
survives is two files' worth of ordinary canvas-terminal code, and the
emulator-facing half of each was replaced by upstream calls. It is
probably better read as "borrow ghostty-web's drawing loop and its mouse
state machine, and write the rest", and on that reading the port is a
head start of a few hundred lines and a day, not a dependency. Whether a
product renderer would keep even that is a question for when the fonts
and graphemes work is done, since that is where the port is no further
on than the minimal renderer and where the one defect found lives.

The more durable finding is probably about the seam rather than about any
of the four. `Frame` took three foreign renderers — a canvas one rebased,
a DOM one driven through its own core interface, and a WebGL2 one fed cell
by cell — each with a shadow-grid adapter and none of them needing the
shape to change. The only widening any of them asked for was a host, a
selection shape and an optional surface element, which is a small price
for being able to swap the renderer under a running measurement. If that
holds, a product could defer the renderer decision considerably longer
than the proposal assumed, and could keep more than one for as long as it
is worth measuring them. Nothing here says which one a product should
want; the case that would decide it — a DOM renderer under sustained
noisy output — has not been run.

## M4 verdict

The stop condition has two halves, and neither is hit.

**The browser decodes what the daemon encodes.** Established in the
first half and unchanged by the second: the same `ghostty-vt-small.wasm`
bytes, the daemon's `GHOSTSNP` snapshot, the two-stage `ready()`-then-
history decode, a replica whose text is identical to the daemon's
`screen` on every check, keys and mouse through the WASM encoders, and
three foreign renderers painting the same `Frame`s without the seam
changing shape.

**The renderer route did not cost more than the rest of the PoC
combined.** My estimate: about one working day and 1,850 lines for the
ghostty-web rebase against M0–M4a's 13,000 lines under `src/` and their
weeks; about a week more to reach the whole gap list, against the same;
and an adapter apiece, of 643 and 461 code lines, for two published
renderers that were never in the proposal's plan. That is an estimate of
effort I did myself, stated as such; the coordinator's own accounting of
the earlier milestones is the other side of the comparison. What the
evidence does say with more confidence: the proposal's worry — "absorbing
a 1,620-line patch against a stale pin" — did not materialise, because no
line of the patch was needed; the cost that did materialise is the
ordinary cost of a terminal renderer's long tail, which ghostty-web shares
rather than removes; and the seam turned out cheap enough to fill that
three different renderers now sit behind it and one session can be run
through each.

What the milestone does not settle is which renderer a product should
want. The repaint numbers above are one window, one browser, one machine
and a still screen, and the case that would separate the four — a DOM
renderer under sustained noisy output — has not been run.
