# M5 — the transport: `ssh -L` under a live PTY, on three platforms

What the proposal's §7 M5 row asks: a machine running `sshd` with the daemon
behind it, `ssh -L` with a Unix socket on each end, a symmetric delay for
latency, and `wp attach` through the forward under `yes` and `vim`. The stop
condition is "frames coalesce badly enough that a TUI is unusable at 50 ms
RTT, or the forward drops under load" — **not hit**, on any platform the
spike has run on. The frame stream came through intact at every RTT, a TUI
redraw arrives as one read, the forward survives a client stalled for
seconds, and a killed forward loses the view and nothing else. Two things
were found that shape the transport without stopping it: OpenSSH leaves
Nagle on for a `-N` forward, which costs a TUI a second round trip per
keystroke, and the daemon's 256 KiB queue bound is a bandwidth-delay product
once a forward is in the way. The verdict is [at the end](#m5-verdict), with
[a paragraph for §8](#for-the-proposals-8).

Three runs, because the far end cannot be the same thing everywhere:

| Where                        | The "remote"                                       | RTT from      | What it can say                                                                           |
| ---------------------------- | -------------------------------------------------- | ------------- | ----------------------------------------------------------------------------------------- |
| linux-x64, one WSL2 machine  | a container on the same kernel                     | `tc netem`    | the whole spike: `yes`, `vim`, a 5 fps TUI, load, recovery and idle at 0, 50 and 200 ms   |
| darwin-arm64, `macos-latest` | the runner itself, behind a private `sshd`         | pf's dummynet | the same tables, with the forward's two ends on one machine                               |
| win32-x64, `windows-latest`  | the runner itself, behind its own `sshd`, over TCP | none          | a Windows `wp` reaching a daemon it did not start, and what a port costs against a socket |

No run has a real network in it: there is no loss and no reordering
anywhere, and every RTT is a shaper's. What each arrangement does and does
not show is spelled out in its own section.

The code is under [`../spikes/m5/`](../spikes/m5): `Dockerfile` and `lib.ts`
(the stand-in terminal, screen comparison, the container and forward
plumbing), `self.ts` (the same machine as the remote, for a host with no
Docker), and `run.ts` (the measurements). `bun run m5 -- --rtt 0,50,200`
runs the whole thing in about nine minutes and prints the tables below;
`--remote self` swaps the container for a private `sshd`. Either tears the
container, the forwards and the daemons down in a `finally`. It is not a
`bun test` — the container needs Docker and the private `sshd` needs
passwordless `sudo` — but it typechecks with the rest, and nothing is left
running afterwards.

## Environment: the Linux run

| Item             | Value                                                                                                                                   |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Host             | Bun 1.3.14, OpenSSH 10.2p1 (Ubuntu), kernel `6.18.33.2-microsoft-standard-WSL2`; Docker Desktop 29.6.2 with the WSL2 backend            |
| Image            | `werk-poc-m5`: `debian:bookworm-slim` + `openssh-server` 9.2p1, `iproute2`, `vim`, `coreutils`, `procps`, and `dist/wp` (95 MB); 341 MB |
| Container        | `--cap-add NET_ADMIN`, `sshd -D` on a port published to `127.0.0.1` only, a `werk` user (uid 1000) with a throwaway ed25519 key         |
| Daemon (remote)  | `docker exec -u werk … wp ls` autostarts it: `XDG_RUNTIME_DIR=/run/user/1000`, `WP_STATE_DIR=/home/werk/.local/state/werk-poc`          |
| Forward          | `ssh -F /dev/null -i <key> -p <port> -o StreamLocalBindUnlink=yes -N -L /tmp/wp-m5-XXXX/wp.sock:/run/user/1000/werk-poc/wp.sock`        |
| Client (host)    | the same `dist/wp`, `wp --socket /tmp/wp-m5-XXXX/wp.sock attach <id>` in a `Bun.Terminal`, fed to a `ghostty-wasm` replica (as M2)      |
| RTT              | `netem delay rtt/2` on the container's `eth0` root and `rtt/2` on its ingress via an `ifb` redirect, so the delay is symmetric          |
| Image afterwards | left tagged `werk-poc-m5`; the keypair, the socket directory and the container are removed                                              |

`dist/wp` links only `libc`, `libm`, `libdl` and `libpthread`, so bookworm's
glibc is enough. The `flock` through `bun:ffi` (`dlopen("libc.so.6")`) works in
the container unchanged, as does the detached autostart from a `docker exec`:
the daemon is pid 41 with `sid == pid` and no tty, and it outlives the exec.

The host-side socket lives in `/tmp/wp-m5-XXXX/`, not under a deeper scratch
directory, because `sun_path` is 108 bytes and the forward binds it.

## What was needed to get there

The client library and the CLI had no way to be pointed at a socket other
than `$XDG_RUNTIME_DIR/werk-poc/wp.sock`. M5 adds one: `connect({ socket })`
in the library, which uses the path as given and never autostarts (nothing on
this end could start a daemon at the far end of a forward), and
`--socket <path>` on every command, before or after the command name, or
`WP_SOCKET` in the environment. That is the whole of the remote client:
`wp --socket … ls` printed the container daemon's (empty) table on the first
try, and the `hello` handshake passed — protocol 1, `wp 0.0.0-poc`, engine
`3c1ef5b3`, the same binary on both ends.

`sshd`'s side of the forward connects to the remote socket as the ssh user,
so the daemon's 0700 runtime directory needs no change: the forward is a
client like any other, and `stats` lists it as one.

## RTT, as applied and as measured

The host cannot ping a container IP under Docker Desktop (the WSL side's
`docker0` has no carrier; published ports go through a proxy), so the RTT was
measured two ways over the path the traffic actually takes: a `stats`
round trip through the forward, and the time from a TCP connect on the
published port to `sshd`'s banner, which is a connect plus one round trip
plus the proxy. A bulk `ssh host head -c 16M /dev/zero` over an exec channel
(handshake included) says what the path itself carries at each RTT, so the
forward's numbers below can be read against it.

| netem RTT | `stats` via forward p50 / p90 | TCP banner p50 | exec channel bulk |
| --------- | ----------------------------- | -------------- | ----------------- |
| 0 ms      | 0.3 / 0.4 ms                  | 5.8 ms         | 81.8 MiB/s        |
| 50 ms     | 51.2 / 51.7 ms                | 111.2 ms       | 11.6 MiB/s        |
| 200 ms    | 201.7 / 202.4 ms              | 410.2 ms       | 3.1 MiB/s         |

The `netem` delay lands exactly. The bulk rate varies a good deal between runs
(17 MiB/s at 50 ms in one probe, 11.6 here) — Docker Desktop's path, not
anything of ours — which is why the `yes` rows also vary between runs.

## `yes | head -c 20M` through the forward

The session is `sh -c 'read x; yes | head -c 20M; echo; echo DONE; read y'`,
started through the forward with the library's `run`; the attach happens
before the Enter that starts it, so the whole stream crosses the forward live.
The line discipline turns 20 MiB of `y\n` into 30 MiB of `y\r\n`. Two clients
attach through the same forward: `wp attach` in a PTY (whose bytes are what
the daemon's `stats` report as sent to that connection) and a library attacher
that counts frames — the protocol is length-framed, so corruption would be a
parse error, which closes the client, and it never was. `queue bound 4 MiB`
rows are a second pass with the daemon restarted under `WP_QUEUE_BOUND`.

| RTT                       | to `wp attach`: sent, wall, rate; lag episodes / bytes dropped | library attacher                          |
| ------------------------- | -------------------------------------------------------------- | ----------------------------------------- |
| 0 ms                      | 27.7 MiB in 3.31 s, 8.4 MiB/s; 7× / 2.3 MiB                    | 2200 frames, 30.0 MiB, 1 render, no lag   |
| 50 ms                     | 27.8 MiB in 3.68 s, 7.5 MiB/s; 7× / 2.2 MiB                    | 2573 frames, 29.4 MiB, 2 renders, 1 lag   |
| 200 ms                    | 13.4 MiB in 4.06 s, 3.3 MiB/s; 11× / 16.6 MiB                  | 1445 frames, 13.5 MiB, 12 renders, 11 lag |
| 0 ms, queue bound 4 MiB   | 30.0 MiB in 3.21 s, 9.4 MiB/s; none                            | 2082 frames, 30.0 MiB, 1 render, no lag   |
| 50 ms, queue bound 4 MiB  | 30.0 MiB in 3.78 s, 7.9 MiB/s; none                            | 2726 frames, 30.0 MiB, 1 render, no lag   |
| 200 ms, queue bound 4 MiB | 21.9 MiB in 4.27 s, 5.1 MiB/s; 2× / 8.1 MiB                    | 2164 frames, 21.9 MiB, 3 renders, 2 lag   |
| local, no ssh             | 27.9 MiB in 3.19 s, 8.8 MiB/s; 8× / 2.1 MiB                    | 1713 frames, 30.0 MiB, 1 render, no lag   |

The final screen matched the daemon's in every row. Three things to read out
of it:

- **The `wp attach` client lags locally too.** Its 7–8 episodes at 0 and 50 ms
  are the same as with no ssh at all: the slow consumer is the harness's outer
  PTY plus a WASM replica eating 40 MiB (the outer PTY's `onlcr` adds a fourth
  byte to every line). The forward adds nothing at 0 or 50 ms; the library
  attacher, which has no PTY behind it, took all 30 MiB with no lag at 0 ms
  and lost one episode at 50 ms.
- **At 200 ms the forward is the slow consumer, and the daemon's rule
  engages through it.** The daemon sees the forward's socket, not the real
  client; when `sshd` stops reading (its channel window is spent and the
  `WINDOW_ADJUST` is a round trip away) the kernel buffer fills, the 256 KiB
  queue fills, and the connection is marked lagging and dropped exactly as
  M2 designed. Delivered throughput settles near what fits in flight per
  round trip: roughly the queue bound plus the two kernel socket buffers,
  divided by the RTT — of the order of 1–3 MiB/s at 200 ms, and in a slower
  run of the same code, 2.1 MiB/s at 50 ms.
- **Raising the bound confirms it.** With the queue at 4 MiB nothing is
  dropped at 0 or 50 ms, and at 200 ms the client gets 22 MiB instead of
  13 — bounded now by the path itself, which carried 3.1 MiB/s on a bare exec
  channel in this run. The bound is a bandwidth-delay product once a forward
  is in the way, and 256 KiB is sized for a Unix socket on one machine.

Nothing was reordered or corrupted at any RTT: every frame parsed, every
final screen matched, and the library attacher's byte count equals what it
was sent.

## vim: keystroke to paint

A 100-line file, 50 keystroke units cycling `10j`, `w`, `→`, `←`, `↓`, `↑`,
`dd` and `:s/foo/bar/⏎`. Each unit is written to the outer PTY at `t0`; the
harness then polls the daemon's `screen` through the forward until the
daemon's screen has changed and the replica shows the same thing on two polls
80 ms apart. The paint time is read afterwards off the timestamps the harness
stamps on every PTY read (each read also records the replica's screen), as the
first read after which the replica showed the settled screen and kept showing
it — so the poll does not enter the number. Every unit settled; every unit's
paint was attributable.

Two forwards were measured, because the first result demanded an explanation:
the ordinary `ssh -N -L …`, and the same `-L` carried by a connection that
also holds a pty session (`ssh -tt -L … host sleep 100000`).

| RTT           | forward | p50      | p90      | p99      | max      | reads per redraw |
| ------------- | ------- | -------- | -------- | -------- | -------- | ---------------- |
| 0 ms          | `-N`    | 32.1 ms  | 33.2 ms  | 35.7 ms  | 35.7 ms  | 1                |
| 0 ms          | `-tt`   | 1.2 ms   | 2.5 ms   | 5.4 ms   | 5.4 ms   | 1                |
| 50 ms         | `-N`    | 133.2 ms | 134.5 ms | 135.0 ms | 135.0 ms | 1                |
| 50 ms         | `-tt`   | 51.2 ms  | 51.9 ms  | 52.3 ms  | 52.3 ms  | 1                |
| 200 ms        | `-N`    | 435.3 ms | 437.2 ms | 438.5 ms | 438.5 ms | 1                |
| 200 ms        | `-tt`   | 202.7 ms | 203.9 ms | 205.8 ms | 205.8 ms | 1 (max 2)        |
| local, no ssh | —       | 1.2 ms   | 2.4 ms   | 3.0 ms   | 3.0 ms   | 1 (max 2)        |

Over `-N` a keystroke costs **two round trips plus about 33 ms**; over `-tt`
it costs **one round trip plus about a millisecond**, which is the floor.
The mechanism, checked with a separate probe rather than inferred: OpenSSH
sets `TCP_NODELAY` on a connection only when it is "interactive", which for
both `ssh` and `sshd` means a session channel with a pty on it. `-N` opens no
session, so **Nagle stays on at both ends of a plain forward**. A vim redraw
reaches `sshd` as more than one small write (locally the harness sees up to
two PTY reads per redraw), the second segment is held until the first is
acknowledged, and the client's delayed ACK holds that for up to 40 ms — hence
`2 × RTT + delayed ACK`. The probe made it plain: a program answering each
key with two writes 1 ms apart cost 3.5 ms at RTT 0 and 102 ms at 50 ms over
`-N`, and 4.8 ms and 54 ms over `-tt`; a single-write echo (`cat`) cost one
round trip either way. The extra 32 ms at RTT 0 in the table is the delayed
ACK alone, exposed by the harness's own poll traffic sharing the connection
— in the product, a session list refreshing or a second session's output
would do the same.

A resize through the forward worked at every RTT: `SIGWINCH` on the outer PTY
became a `resize` request, the daemon's screen went to 100×30, vim redrew,
and the replica matched.

## What arrives in one read

Sizes of the outer PTY's `data` callback chunks, i.e. what `wp attach` handed
the terminal per write:

| RTT           | during `yes` (reads × p50 / p90 / max) | during vim (reads × p50 / p90 / max) |
| ------------- | -------------------------------------- | ------------------------------------ |
| 0 ms          | 2054 × 15.1 KB / 38.0 KB / 136.0 KB    | 56 × 7 B / 336 B / 997 B             |
| 50 ms         | 2486 × 11.6 KB / 32.1 KB / 107.2 KB    | 57 × 7 B / 336 B / 997 B             |
| 200 ms        | 1178 × 12.0 KB / 32.4 KB / 136.9 KB    | 57 × 7 B / 336 B / 997 B             |
| local, no ssh | 2197 × 14.3 KB / 36.8 KB / 132.5 KB    | 63 × 64 B / 361 B / 966 B            |

Under `yes` the distribution is the same with and without ssh: the reads are
shaped by the daemon's PTY reads (about 12 KB each, 2200–2700 output frames
for 30 MiB) and the CLI's writes, not by the forward. Under vim the forward
_reduces_ fragmentation: a redraw that locally sometimes lands in two reads
arrives through ssh as one, because `sshd` coalesces the daemon's back-to-back
frames into one channel packet. The 7-byte median is the cursor-only
responses to arrow keys, which are one frame anywhere. Nothing batches
several redraws into one read: the frame count per keystroke is one.

## A 5 fps TUI for 30 s

A shell loop printing `counter: N` at the top of the screen every 200 ms for
150 frames, attached through the forward before it starts:

| RTT    | frames seen | reads | gap p50 / p99 / max      |
| ------ | ----------- | ----- | ------------------------ |
| 0 ms   | 150 / 150   | 151   | 201.0 / 202.5 / 202.6 ms |
| 50 ms  | 150 / 150   | 153   | 201.2 / 205.1 / 238.1 ms |
| 200 ms | 150 / 150   | 153   | 201.6 / 241.4 / 452.5 ms |

Every frame arrived, one per read, no lag episode. At 50 ms the cadence is
what the program produced, to a few milliseconds; at 200 ms one frame in a
hundred arrives 40–250 ms late and the next one early, which is the same
Nagle-and-delayed-ACK shape as above (this run used the `-N` forward).

Is a TUI usable at 50 ms? By the numbers: 51 ms keystroke-to-paint over a
connection with `TCP_NODELAY`, 133 ms over a bare `-N` forward, every redraw
in one piece, a 5 fps animation delivered at 5 fps. The first is
indistinguishable from the network's own latency; the second is noticeable
and still usable, and it is a property of how the forward is opened, not of
forwarding.

## The forward under load, and recovery

At 50 ms RTT, with `yes` streaming unbounded through the forward to
`wp attach` in a PTY:

- **`SIGSTOP` the host `wp attach` for 3 s.** The `ssh -N` stays up. On the
  container side the daemon marks the forward's connection lagging within the
  stall, with 0.1 KiB queued and 21.7 MiB dropped by the time it was asked —
  the drop rule sees the forward's socket back up exactly as it would a slow
  local client. During the stall a second connection through the same forward
  answered `stats`: one stalled channel does not block another on the same
  ssh connection.
- **`SIGCONT`.** 25 MiB more arrive, the client sees three renders (the
  resume re-emissions), the connection is no longer lagging; three lag
  episodes and 27.3 MiB dropped in all. The forward never dropped.
- **Kill `ssh -N` mid-stream.** `wp attach` exits 1 after 43 ms with
  `[wp: lost the connection to the daemon; session c7dc33 may still be running]`
  and the terminal restored. That is new: the attach loop had no handler for
  the socket closing without an `exited` or a detach reply, and the first M5
  run found it waiting forever with `yes` frozen on screen. `attachInteractive`
  now watches `client.waitClosed()`.
- **A new forward.** `ls` through it shows the session running with no
  clients; `wp attach` through it paints and matches the daemon's screen.

## Idle

A forwarded attach to an idle vim, nothing typed for 120 s (no
`ServerAliveInterval`, no `ClientAliveInterval`, the defaults): `ssh -N` still
up, and `j` painted in 3.8 ms at RTT 0. Docker Desktop's port proxy imposed no
idle timeout at that scale; a real NAT might, and `ServerAlive*` is the
research's answer to that, untested here.

## M5 verdict

**The stop condition is not hit.** Frames do not coalesce badly — the opposite:
a TUI redraw arrives in one read through the forward, and nothing merges
consecutive redraws. A TUI at 50 ms RTT paints in one round trip when the
connection has `TCP_NODELAY`, two when it does not, and either way every
keystroke settled and every screen matched. The forward did not drop under
load: it survived a client stalled for 3 s and a 30 MiB flood at every RTT,
the daemon's backpressure rule engaged through it, and a killed forward cost
the view and nothing else. All of this is one machine and `netem`; real
networks add loss and reordering, which nothing here exercised.

## For the proposal's §8

§8's last row asks whether the forward needs framing of its own or a TCP
loopback landing. On this evidence it probably needs neither: the daemon's
length-framed stream crossed the forward intact at every RTT, and the Unix
socket on each end is not where the latency comes from. Two things do look
like they belong in the transport's design, and neither is about the socket:

- **`TCP_NODELAY` has to come from somewhere.** The `ssh` binary sets it only
  when the connection carries a pty session, so a transport built on
  `ssh -N -L` probably pays two round trips per keystroke unless it also opens
  a pty session on the same connection (the `-tt … sleep` form measured here)
  or is replaced by an in-process ssh client that sets the option itself —
  which is the direction `09-remote-transport.md` §2 already leans for
  multiplexing reasons. Whether `sshd` on an arbitrary host can be made to set
  it without a pty is a question nobody has answered.
- **The queue bound is a bandwidth-delay product.** 256 KiB is right for a
  local socket and starts dropping output at a few MiB/s once a round trip is
  in the path. It probably wants to scale with an RTT the client measures at
  `hello`, or give way to accounting of what is in flight per connection;
  raising it is cheap and the daemon already has the override.

A TCP loopback landing would change neither; Windows may still want one for
its own reasons (`09-remote-transport.md`'s Win32-OpenSSH caveat), and that
remains untested.

## What changed in the daemon and client for this

- `client/index.ts`: `connect({ socket })` — an explicit socket path, used as
  given, never autostarts.
- `cli/main.ts`: `--socket <path>` (before or after the command) and
  `WP_SOCKET`, threaded through every command.
- `cli/attach.ts`: the attach loop ends, restores the terminal and says so
  when the connection closes under it.
- `daemon/connection.ts`: `WP_QUEUE_BOUND` overrides the 256 KiB bound, for
  the experiment above; the default is unchanged.
- `daemon/launch.test.ts`: one test for the explicit socket path (a symlink
  standing in for a forward; a missing socket rejects and starts nothing).
