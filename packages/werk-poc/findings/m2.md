# M2 — the daemon, the protocol, the CLI, and backpressure

What the proposal's §4 asks of M2: a daemon that owns a PTY per session, a
wire protocol that is the only interface to it, re-emission of the screen on
reattach, per-client bounded queues with the lagging-client rule, and the
interactive `wp run` / `attach` / `ls` / `kill` on top with a detach key. The
stop condition is "reattach into a real terminal is visibly wrong for `vim`
or an agent, or a slow client stalls a fast one" — **not hit**. The evidence
is in [the fidelity table](#reattach-fidelity-the-stop-condition-measured) and
[the end-to-end slow-client run](#a-slow-client-does-not-stall-a-fast-one-end-to-end).

The code is under [`../src/`](../src): the protocol in `protocol/`, the daemon
in `daemon/`, the programmatic client in `client/`, the commands in `cli/`.
Tests drive a real daemon in a temporary `XDG_RUNTIME_DIR` and tear it down;
the fidelity scenarios in [`../spikes/m2/`](../spikes/m2) drive the compiled
`wp` inside a PTY of their own. `bun test` is 119 across 12 files (the eight fidelity scenarios run as one
test in a process of their own), and no daemon or `wp attach` is left
behind.

The first half of this file is the daemon; the CLI starts at
[The CLI](#the-cli-raw-mode-the-detach-key-and-what-bun-offers).

## The socket, the lock, the readiness handshake — and which Bun APIs expressed them

Every mechanism `04-daemon-best-practices.md` names was buildable in Bun; the
one that needed care is readiness.

| Mechanism                           | How, in Bun                                                                             | Result                                                                                                                           |
| ----------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Unix socket                         | `Bun.listen({ unix })` / `Bun.connect({ unix })`                                        | Works. `SocketHandler` gives `open`/`data`/`drain`/`close`/`error`; the server socket carries per-connection `data`.             |
| `flock` before bind                 | `bun:ffi` `dlopen("libc.so.6", { flock })`, `LOCK_EX\|LOCK_NB`                          | Works, compiled too (libc is resolved at run time). Bun has **no** flock API — no `fs` call, no `Bun.file` lock. FFI is it.      |
| Atomic bind-then-rename             | bind a `.wp.sock.<pid>.tmp` name, `fs.renameSync` onto `wp.sock`                        | Works. The rename replaces a stale socket in one step, closing the unlink/bind race. `chmod 0600` on the temp before the rename. |
| Detach                              | `Bun.spawn({ detached: true, stdio: ["ignore","ignore","ignore","pipe"] })` + `unref()` | Works, as M0 found: `detached` calls `setsid`, no double fork. The daemon reaches `sid == pid` with `tty ?`.                     |
| Readiness pipe                      | a 4th `"pipe"` stdio slot; child writes to fd 3; parent reads `proc.stdio[3]`           | Works, **but not reliably enough to wait on alone** — see below.                                                                 |
| No PID file, no signals for control | socket presence is liveness; `ls`/`kill`/`detach`/`shutdown` are round-trips            | Works. `SIGTERM`/`SIGINT`/`SIGHUP` only trigger the same graceful shutdown.                                                      |

### The readiness pipe stalls under load; the socket `hello` is the authority

Passing a pipe as `stdio[3]` works: `proc.stdio[3]` is the parent's read fd and
the daemon sees it as fd 3. The daemon writes `ready\n` and closes it. Two
wrinkles:

- **The fd is non-blocking.** `fs.readSync(fd, …)` returns `EAGAIN` immediately.
  It has to be read asynchronously; `Bun.file(fd).text()` reads it to EOF.
- **That async read was seen to hang past a 10-second deadline inside `bun test`**,
  where the process has many open fds (the readiness fd came back as fd 53) and a
  busy event loop, even though the daemon had already written and closed its end
  (confirmed: the daemon's log showed it listening, and a manual `spawnDaemon`
  in the same conditions returned `"ready\n"` in ~23 ms). Standalone it is
  always fast; under contention it is not dependable.

So the launcher treats the pipe as an optimisation and an error channel, not as
the truth. `ensureDaemon` polls the socket with a `hello` (exponential backoff,
10 ms→200 ms) until it succeeds or a deadline passes; a `"ready\n"` on the pipe
lets it try the first connect immediately, and an `error: … lock` line lets a
race loser skip straight to polling the winner's socket. The pipe read itself is
bounded to 3 s and a timeout just yields `""` (unknown → go poll). This is the
§4 note "if not, fall back to polling the socket until `hello` succeeds" — it
was needed. Autostart to a completed `hello` is **~27 ms**; a bare spawn to the
ready token when the pipe does resolve is **~24 ms**.

### The ad-hoc spawn race

Three launchers starting at once end up on one daemon: all three fail the first
probe, all three spawn, one wins the `flock`, the two losers' daemons report
`already holds the lock` on their pipe and exit, and the loser launchers poll
until the winner's socket answers. A killed daemon leaves a stale socket **and**
a stale lock; the kernel drops the lock when the process dies (even as a
zombie), and the next daemon's bind-then-rename replaces the socket. Both are
tested.

### One `Bun.Terminal` subtlety M0 did not cover

M0 spawned the child with inline `terminal: {…}` options and found the PTY
became the child's controlling terminal. It turns out **that only holds for the
inline form**. Passing a pre-constructed `new Bun.Terminal(...)` as the
`terminal` option spawns the child in the _daemon's_ session with `tty ?` and no
controlling terminal, so Ctrl+C and `SIGWINCH` never reach it. The daemon
therefore spawns with inline options and reads `proc.terminal` back. Measured
directly:

```
inline options:   child pid==pgid==sid, tty pts/N, stat Ss+   (controlling terminal)
Terminal object:  child ppid==daemon,  sid==daemon's, tty ?,  stat S   (no tty)
```

This held whether the daemon itself was a normal process or detached. It is the
one thing about `Bun.Terminal` that bit M2 and was not in M0.

The `exit` callback is used only as a hint (`ptyDone`), never as the child's
fate, exactly as M0 said: the child's code/signal come from `proc.exited` /
`proc.exitCode` / `proc.signalCode`, and the handler is idempotent. After the
child exits the daemon waits up to 500 ms for the PTY's EIO (so the child's last
output is delivered) before calling `terminal.close()`.

## The protocol

One file, `protocol/index.ts`, imported by the daemon, the client, and — since
it has no Bun-specific imports — a browser bundle later. Framing:

```
┌────────────┬──────┬──────────────────────┐
│ u32 LE len │ type │ payload (len-1 bytes) │   len covers type+payload
└────────────┴──────┴──────────────────────┘
```

Four frame types: `control` (UTF-8 JSON), `input`, `output`, `render` (raw
bytes). Keeping input/output/render out of JSON keeps the hot path free of
encode/parse and base64. A client request carries a `rid`; the daemon answers
with one `reply` or `error` bearing the same `rid`. Notices (`exited`,
`lagging`, `resumed`, `effect`) carry no `rid`. `FrameParser` is a streaming
reassembler — a frame may span many socket reads, and many frames may arrive in
one — with copied payloads; it is unit-tested against byte-by-byte splits,
header splits, and 300 KB frames in 1 KB pieces.

Messages:

| Message                                     | Direction | Carries                                                                                             |
| ------------------------------------------- | --------- | --------------------------------------------------------------------------------------------------- |
| `hello`                                     | both      | protocol version, wp version, engine pin SHA; daemon refuses a mismatch                             |
| `run`                                       | c→d       | `{argv, cwd, env, cols, rows, engine}` → `{id}`                                                     |
| `attach`                                    | c→d       | `{id, cols, rows, readOnly}` → `{id, status, exitCode, signalCode}`                                 |
| `detach` / `resize`                         | c→d       | drop this client (reply says whether the session is on the alternate screen) / set the session size |
| `input`                                     | c→d       | raw bytes to the PTY (ignored for a read-only attacher)                                             |
| `output`                                    | d→c       | raw PTY bytes, live                                                                                 |
| `render`                                    | d→c       | a clear (`CSI H CSI 2 J`) + re-emitted viewport; after attach and after lag                         |
| `ls`                                        | c→d       | session list                                                                                        |
| `kill`                                      | c→d       | signal a running session, or remove an exited one                                                   |
| `logs`                                      | c→d       | `{id, format: text\|vt}` → the whole active screen incl. scrollback                                 |
| `screen`                                    | c→d       | `{id}` → the viewport as plain text, cursor, alt-screen flag; for the fidelity harness              |
| `stats`                                     | c→d       | daemon pid, RSS, per-connection backpressure accounting                                             |
| `exited` / `lagging` / `resumed` / `effect` | d→c       | notices to attached clients                                                                         |
| `shutdown`                                  | c→d       | end the daemon (a round-trip, not a signal)                                                         |

On a `hello` mismatch (protocol, wp version, or engine pin) the daemon sends one
`error` with code `version-mismatch` and a plain message — "stop the daemon and
start it from this wp; that ends its sessions" — and closes. It does not bridge,
per §3. The client surfaces it as a `DaemonError`, and an autostart is not
triggered by a mismatch (the daemon answered, so it is not "absent").

## Attach, reattach, and the render contract

On attach the daemon resizes the session's VT and PTY to the attacher's size
(the daemon owns the size), then sends one `render` frame: `CSI H CSI 2 J`
followed by `emitVt({ cursor: true, style: true, scrollback: false })` — the
viewport only, with the cursor placed and pending SGR restored. Then it streams
`output` live. The **reattach-fidelity test** proves the mechanism: run
`echo one; sleep 1; echo two; sleep 30`, attach and see `one`, detach, let
`two` print with nobody attached, reattach — the single render frame contains
both `one` and `two` and places the cursor at row 3, with no `output` yet. That
is the whole point of the daemon holding a live emulator rather than a byte log.

**Viewport only, `logs` for history.** The first paint is the viewport because
that is all a CLI in someone else's terminal can be handed cleanly (§2), and
because the soft-wrap defect M1 measured is confined to re-emission; `logs`
(text or VT, both offered) returns the whole active screen including scrollback
for when history is wanted. The alternate-screen and resize-reflow fidelity that
§6 calls for is a bench axis, not built here.

**Size ownership is a product question.** The daemon owns the PTY size and the
most recent attacher wins — a second attacher at 100×30 resizes a session a
first attacher put at 120×40, and the first attacher is not told. That is fine
for one user on two terminals and wrong for two users; the product will have to
decide whether later attachers are clamped, told, or refused. Recorded, not
resolved.

Multiple simultaneous attachers work (both get every `output`); a read-only
attacher's `input` frames are dropped at the daemon; detach just removes the
client and the session continues.

## Backpressure — the §4 rule, measured

Each connection has a bounded outbound queue (`QUEUE_BOUND = 256 KiB`). The
accounting has two stages: `socket.write()` returns the bytes the kernel
accepted (it can be short, or `-1` when closed) and the `drain` handler fires
when the kernel has room again; the queue holds only what the kernel would not
take. `output` frames are droppable, `control` and `render` frames are not. When
a droppable frame would push the queue past the bound, the connection drops its
queued output (keeping any half-written head frame, which cannot be cut), marks
itself lagging, and sends a `lagging` notice. While lagging it queues nothing
droppable. When the queue finally drains it clears the flag and sends a fresh
`render` (re-emission) followed by `resumed`, then resumes streaming. Input is
never blocked and the PTY is never paused.

The slow-client test: two clients attach, `yes | head -c 8M` runs (the line
discipline turns each `y\n` into `y\r\n`, so ~12.6 MB reaches the daemon), and
one client stops reading its socket (`socket.pause()` in Bun — it exists and
works). A representative run:

| Quantity                                 | Value                                     |
| ---------------------------------------- | ----------------------------------------- |
| Queue bound                              | 262,144 B                                 |
| Fast client received                     | 12,582,918 of 12,582,912 B, **no lag**    |
| Slow client dropped                      | 12,366,894 B over **1** lag episode       |
| Slow client max queue                    | 252,848 B (**under** the 262,144 B bound) |
| First short write after                  | 221,458 B accepted by the kernel          |
| Short writes / drains on the slow client | 1 / 1                                     |
| Drain latency (last short write → drain) | 1,454 ms                                  |
| Slow client output actually delivered    | < 6.3 MB (most of it dropped)             |
| Slow client renders                      | ≥ 2 (the attach paint, then the resume)   |
| Daemon RSS                               | 64.7 → 71.1 MiB, flat after               |

**Does Bun's write signal arrive in time?** Yes, comfortably, and this answers
§8's worry ("a lagging client cannot be detected before its queue grows past the
threshold"). The kernel's own socket buffer absorbs the first ~221 KB before
`socket.write` first returns short; from there the daemon's own queue accounting
takes over, and because the queue is checked on every enqueue the client is
marked lagging the instant the _queue_ (not the kernel buffer) would exceed
256 KiB — the max queued never crossed the bound. A separate isolated spike
(`Bun.connect` client paused, server writing 16 KiB chunks) confirmed the shape:
`socket.write` returned `0` after ~213 KB the kernel had swallowed, and `drain`
fired ~206 ms later once the client resumed, ~0.6 ms after the resume. So Bun's
write-return-value plus `drain` are usable for backpressure without a timer, and
the daemon needs no separate byte-counting on the kernel side beyond reading the
return value. RSS stayed bounded (a ~6 MB working-set bump during the flood, no
growth after) — the queue never accumulated the flood, it dropped it.

`socket.pause()` / `resume()` are real Bun `Socket` methods and are what a slow
reader is simulated with; the fast client shares nothing with the slow one
(separate queue, separate socket), so it never lagged.

## The CLI: raw mode, the detach key, and what Bun offers

The interactive commands sit on `client/index.ts`; the loop that owns the
terminal is `cli/attach.ts`, and `cli/main.ts` is a ~40-line hand-rolled
parser plus one function per command. Everything below was measured under a
`Bun.Terminal` PTY on Bun 1.3.14, interpreted and as the compiled `dist/wp`.

| Need                | What Bun offers                                                                                                                                                                                                                                                                                                                                 | Chosen, and why                                                                                                                                                                                                                                                                                                                                                                |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Raw mode on stdin   | `process.stdin.setRawMode(true)` exists and works; `isRaw` follows it. After it, `process.stdin.on("data")` delivers every byte as typed — `ab`, `^C` as `0x03`, `ESC [ A`, `^\` as `0x1c` — and so does `for await (const c of Bun.stdin.stream())`. Like libuv's, Bun's raw mode clears `icanon`/`echo`/`isig` and **keeps `opost`**.         | `process.stdin`: it pauses and resumes, carries `isRaw`, and is what a Node-shaped restore expects. `Bun.stdin` would do too.                                                                                                                                                                                                                                                  |
| Writing to stdout   | `/proc/self/fdinfo` shows fds 0 and 1 stay **blocking** (`flags 02`, no `O_NONBLOCK`) before and after raw mode and after stdin reads begin. `fs.writeSync(1, 1 MiB)` completed in 12 ms with zero `EAGAIN`. `process.stdout.write`, `Bun.write(Bun.stdout)` and `fs.writeSync` all delivered 4 MiB of 64 KiB marker chunks in order in ~27 ms. | `fs.writeSync` in a loop. It is ordered by construction — a render written after an output frame lands after it — and blocking is the point: a slow terminal stalls this process, the socket fills, and the daemon applies the lagging rule to this client alone. The async paths order too, but nothing says they must, and `Bun.write` needs draining before `process.exit`. |
| Size and `SIGWINCH` | `process.stdout.columns`/`rows` are set under a PTY and update on resize; `process.on("SIGWINCH")` fires in Bun.                                                                                                                                                                                                                                | Read the size on each `SIGWINCH` and send `resize`. Measured: the outer PTY resized to 120×35 and the daemon's session followed.                                                                                                                                                                                                                                               |
| Signals to the CLI  | `process.on("SIGINT"/"SIGTERM"/"SIGHUP")` and `process.on("exit")` all fire.                                                                                                                                                                                                                                                                    | All four restore the terminal. `^C` never reaches these handlers — raw mode makes it a byte for the session — so they only cover a `kill` of the client, and they leave the session running and say so.                                                                                                                                                                        |

**Two more things about input, found the hard way.** `Bun.Terminal.write()`
returns the bytes the kernel took _immediately_ — 11,776 of a 1 MiB write to
a `cat` under a PTY, and `0` once the slave's input queue is full — but it
queues the rest and delivers it: all 1 MiB reached `cat`. So the daemon's
`session.input()` and the harness's `terminal.write` are not lossy, and the
return value is not a reason to retry. And `process.stdin` keeps Node's
semantics: `resume()` puts it in flowing mode, and a flowing stream with no
`data` listener discards what it reads, so the CLI installs the listener
before `resume()` and queues bytes that arrive before the attach reply.

**The detach key.** `ctrl-\` (`0x1c`) is looked for in every stdin chunk;
bytes before it are forwarded, it and anything after are not. Then a `detach`
round trip (the reply says whether the session is on the alternate screen —
see below), the terminal is restored, `[detached <id>]` is printed, exit 0.
With `isig` off the key never becomes `SIGQUIT`, and `^C`, `^Z` and `^D` all
belong to the session. Restoration is one idempotent function — raw mode off,
stdin paused, optionally `CSI ? 1049 l`, then `\r\n` — reached from the detach
path, the `exited` notice, the signal handlers, the `exit` hook, and a failed
attach.

**Ordering of the first paint.** The daemon's `render` frame can arrive in the
same socket read as the `attach` reply. Frame handlers fire synchronously
while the reply resolves through a microtask, so by the time `await attach()`
returns the first paint has often already been delivered to the handler. The
CLI holds those bytes until the reply is in hand, because the alternate-screen
switch has to precede them, then writes them in order. Anything built on
`client.attach` with a handler that depends on the reply will hit the same
thing.

**Exit and lag.** The `exited` notice restores the terminal, prints
`[exited <id>: code N]` (or the signal name) and exits with the child's code
(1 for a signal). Nothing is written during a lag — any status line would be
painted over by the render that ends it — and the detach line says
`(lagged N×)` if it happened.

**The rest.** `wp run` with stdin not a tty starts the session and prints the
id; with a tty it attaches through the same path as `wp attach`. `--cols`/
`--rows` override the terminal's size for both. `wp attach` does not autostart
a daemon (nothing to attach to); `run` and `ls` do. An unknown id is
`wp: no session <id>`, exit 1. `wp kill --rm` waits for the exit and removes
the record. `wp logs [--vt]` prints the whole active screen with scrollback.

### `socket.write` can return 0 on an idle socket, and the client has to queue

The one intermittent failure this half produced, and the most useful Bun
fact in it. Across repeated runs of the full suite, roughly one run in three
had a scenario hang until its 60 s timeout: a `wp attach` that never saw a
`ctrl-\`, a `top` reattach that never got its `q`. The trace inside `wp
attach` showed it attached and receiving output for the whole minute with
no stdin ever arriving — the harness had stopped before sending any,
awaiting a daemon reply that never came. A request timeout on the client
turned the hang into a named error, and a check on the write's return value
named a cause:

```
short write sending ls: 0 of 23
```

The harness's `Client` — the same library `wp` uses — called
`socket.write(frame)` for a 23-byte control frame on an idle Unix socket
and got `0` back. Bun's `socket.write` returns what the kernel took and
queues nothing; the daemon's `Connection` already knew this and keeps its
own queue, but the client ignored the return value, so a request could be
silently dropped, and every `await` behind it waited forever. The client
now sends every frame — hello, requests, input — through a queue that keeps
what the kernel refuses and continues on `drain`, exactly as the daemon
does; `requestTimeoutMs` is available for callers that would rather fail
than wait. **Anything on a Bun socket must treat `write` as best-effort and
own a queue**, both directions, however small the frame and however idle
the socket. M4's web server will be a Bun socket in both roles and inherits
this directly.

That fixed the dropped-request case but not the whole pattern. With the
queue in, the full suite still lost about one run in three, with a
different symptom each time — `wp run` got `EPIPE` writing its id to a pipe
the harness was reading, a queued `screen` request got no reply, a `wp
attach` never reached its attach. Pairing the fidelity file with each group
of preceding test files was decisive: with `daemon/launch.test.ts` in the
same process it failed **3 of 3**, always on the harness client's very
first request after connecting (`screen`, rid 1, 10 s timeout, daemon alive
and answering the next connection's `shutdown`); with every other file it
passed 3 of 3, and alone it passed 6 of 6. `launch.test.ts` is the file
that exercises the readiness pipe directly — the `Bun.file(fd).text()` read
that this document already records as stalling under `bun test`, raced
against a timeout and then `fs.closeSync`'d. A read still pending on a
closed fd whose number is later reused is the shape that would explain a
pipe, a socket or a PTY dying under a later owner, but that is a hypothesis;
the mechanism was not pinned down. What was done: the fidelity scenarios
run in a process of their own (`fidelity.test.ts` spawns `run-all.ts` and
asserts on its table), which is also how they are meant to be run. What is
left open, and worth a Bun issue once reduced: a stalled `Bun.file(fd)`
read on a pipe from `Bun.spawn`, followed by closing the fd, appears to
break a later `Bun.connect` client in the same process.

### A render frame, raw

The first frame after attaching to a 60×12 shell that had printed a red word:

```
ESC[H ESC[2J
$ echo hello world CR LF
hello world CR LF
$ printf '\e[31mred\e[0m\n' CR LF
ESC[0m ESC[38;5;1m red ESC[0m CR LF
$ ESC[5;3H ESC[0m
```

The clear, the five used rows, a `CUP` to (row 5, col 3), and an SGR reset for
the pending style. Two things worth knowing: the formatter re-emits colour in
its own form — `38;5;1` for the `31` the program wrote, the same cell either
way — and the outer PTY's `onlcr` (raw mode keeps `opost`) turns each `CR LF`
into `CR CR LF` on the way to the terminal, which is harmless.

### The alternate screen on attach and detach

The daemon can tell whether a session is on the alternate screen (the WASM
adapter's `decMode(1049)`, read through duck typing; it is not on the seam),
and reports it in the `attach` and `detach` replies. The CLI mirrors it:
`CSI ? 1049 h` before the first paint when the session is on it, and
`CSI ? 1049 l` on detach when it still is. `WP_ALT_SCREEN=0` turns the mirror
off. Both were run against `vim` with three shell lines painted on the
stand-in terminal beforehand, standing in for what the user's shell had on
screen:

| Mirror  | While attached | After `ctrl-\`                                                                                                                           |
| ------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **on**  | alt screen     | Primary screen back, the three pre-attach lines intact (`$ ls` on row 0), `[detached <id>]` under them. What tmux does.                  |
| **off** | primary        | `vim`'s screen stays painted, the pre-attach lines are gone, `[detached <id>]` lands at the cursor. The user's scrollback has vim in it. |

When `vim` exits while attached its own `1049 l` passes through verbatim and
the terminal is back on the primary screen either way. `top` on this machine
never enters the alternate screen (no `1049` in its VT), so for it the mirror
is a no-op and the check is that daemon and terminal agree on the state.

The mirror is probably what a product wants, and it is the cheap half of the
question. The other half is left open: a session on the _primary_ screen is
painted over the user's visible screen (the render starts with `CSI 2 J`),
which the terminal's scrollback then holds. Attaching always into the
alternate screen would keep the user's terminal pristine at the cost of the
session's history being reachable only through the daemon (`logs`, or
whatever the product does) rather than the terminal's own scrollbar. Both are
defensible; neither is decided.

### Reattach fidelity — the stop condition, measured

The harness in [`../spikes/m2/`](../spikes/m2) runs the compiled `wp` inside a
`Bun.Terminal` of its own and feeds every byte it writes into a fresh
`ghostty-wasm` terminal — the stand-in for the user's terminal, using the same
emulator the daemon runs. After each step the stand-in's `plainText()` and
cursor are compared with the daemon's own `screen` for the session (and
`styledCells()` where colour matters). Each scenario gets a temporary
`XDG_RUNTIME_DIR` and its own daemon. `bun run spikes/m2/run-all.ts` prints
the table; `spikes/m2/fidelity.test.ts` asserts it under `bun test`. All of
it runs in about 13 s.

| Scenario                                                         | What was compared                                                                                                                                                     | Result                                                                                                                                         |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Shell with coloured lines                                        | Screen and cursor after attach; `red` is palette 1, `bold green` is bold palette 2 in the stand-in's cells; screen after typing a command; `ctrl-\`; `ls`; `logs`     | **Identical.** `[detached]` printed, `ls` shows `running` with 0 clients, `logs` has the typed output                                          |
| `vim` on 100 lines: run, detach, reattach, `:q!`                 | Screen and cursor at first attach; after `10jw` (cursor (5,10)); after detach and a fresh `wp attach`; alternate screen mirrored; `:q!` through the reattached client | **Identical** at every step, cursor restored at (5,10); `[exited <id>: code 0]`, `wp` exits 0, terminal back on primary; `ls` says `exited(0)` |
| `vim`, reattach at 100×30 after 80×24, then `SIGWINCH` to 120×35 | Daemon's session size; screen after `vim` redraws (28 file rows visible at 30 rows); size and screen after the outer PTY is resized while attached                    | Daemon resized to 100×30 then 120×35; **identical** screens at both sizes                                                                      |

### A slow client does not stall a fast one, end to end

Two `wp attach` processes on one `bash` session. The slow one is a
`UserTerminal` in the harness and gets `SIGSTOP` for two seconds; the fast one
runs under [`pty-cat.ts`](../spikes/m2/pty-cat.ts), a process of its own that
does nothing but drain what the client writes and forward stdin. It offers
three sinks, chosen with `WP_M2_SINK`: a PTY, which is what a terminal gives
a client and what this table measures; a pipe, with no line discipline in the
path; and a regular file the client writes itself, which can apply no
back-pressure at all. All three reach the figures below here, and
[platforms.md](./platforms.md#back-pressure-an-8-kib-socket-buffer-against-linuxs-208-kib)
is where the other two earn their keep. Then
`yes | head -c 4M; echo FLOOD-$((1+1))-DONE` is typed into the fast one. A
representative run:

| Quantity                                          | Value                                                                          |
| ------------------------------------------------- | ------------------------------------------------------------------------------ |
| Flood, typed to marker seen by the fast client    | **655 ms**                                                                     |
| Fast client: lines received                       | **2,097,152 of 2,097,152** (8,388,706 B at its PTY)                            |
| Fast client: lag episodes / short writes / drains | **0** / 0 / 0; max queue 100,191 B                                             |
| Slow client: dropped                              | 6,075,963 B in **1** episode                                                   |
| Slow client: max queue                            | 256,328 B (bound 262,144 B); kernel took 217,619 B first                       |
| Daemon RSS during the flood                       | 63.1 MiB                                                                       |
| After `SIGCONT`                                   | a `render` arrives, nobody lagging, both screens **identical** to the daemon's |
| Fast client's final rendering vs the daemon       | replayed into a fresh terminal: **identical**, cursor (2,23)                   |

`pty-cat.ts` exists because of a first attempt that is itself a finding. With
the fast client's PTY drained by the harness process — which was also feeding
8 MB into a WASM emulator inline, and under `bun test` was sharing a heap
with every earlier test file — the "fast" client lagged too: once in
isolation (266 KB dropped), twice in the full suite (578 KB). The arithmetic:
the daemon produces ~10 MB/s here, the PTY holds ~64 KB and the socket
~215 KB before the daemon's own 256 KiB queue starts filling, so **a terminal
that pauses for ~50 ms is a lagging client**. The rule handled it exactly as
designed — drop for that client, repaint when it drains, the other client
untouched — and the final screens agreed. But it says the bound is really a
time budget, and 50 ms is inside the range of an ordinary GC pause or window
move in a real terminal. A product probably wants a larger bound, or one
expressed in time, or both; what it must not do is read a lag as a fault.

### Verdict against the stop condition

**Not hit.** Reattach into `vim`, into `top`, and into a redrawing
alternate-screen TUI is not visibly wrong: every comparison of the stand-in
terminal against the daemon's screen was identical, cursor included, across
detach, reattach, a size change on reattach and a `SIGWINCH` while attached.
A stopped client cost the running one nothing — every line, no lag, no short
write — and the stopped one came back to a correct screen. The one caveat is
the 50 ms figure above, which is a tuning question, not a mechanism failure.

## What M3 and M4 need to know

**The session model** (`daemon/session.ts`). A `Session` is a child process, a
`Bun.Terminal`, a `VtTerminal` tap, and a set of attached `Connection`s.
`status` is `running` | `exited` | `corpse`; `corpse` is reserved and nothing
produces it yet. The constructor always spawns; **a restored corpse needs a
second construction path** with a VT from `engine.decodeState()`, no PTY,
`input` and `resize` of the PTY skipped, `attach` still sending a render, and
the `exited` notice the daemon already sends for a non-running attach carrying
something a CLI can tell apart from a real exit. `render()` is
`CSI H CSI 2 J` + `emitVt` of the viewport; `screen()` is its plain-text
twin. `altScreen()` and `logs` reach past the seam into the WASM adapter
(`decMode(1049)`, `fullText`) by duck typing; a second engine would need
both or lose them gracefully.

**The shutdown hook.** `server.shutdown()` in `daemon/server.ts` is
synchronous, ends every connection, disposes every session, unlinks the
socket, and schedules `process.exit(0)` 50 ms later; `SIGTERM`/`SIGINT`/
`SIGHUP` all call it. M3's snapshot-on-exit goes before the disposes, and
`vt.encodeState()` is already on the seam. The timer snapshot needs nothing
from the CLI.

**What the CLI would do with a corpse.** `attach` replies with `status`, and
`attach.ts` restores and exits on the `exited` notice that follows. For a
corpse it should say so — `[corpse <id>: restored from a snapshot, read-only]`
— rather than `[exited]`; that is one branch on `att.status`.

**For `wp serve`.** The client library is Bun-only (`Bun.connect`), which is
fine for a Bun web server in front of the daemon; the browser gets frames over
a WebSocket. `render` frames are VT re-emission, which the browser does not
want — it wants state transfer — so M4 needs either a `snapshot` request
(`{id}` → `encodeState()` bytes) or the web server living inside the daemon.
`screen` is the shape of a plain-text fallback. Size ownership is still
"the most recent attacher wins", so a browser tab attaching will resize the
CLI's session; `ls` reports `cols`/`rows`/`attachedClients` for whatever the
web UI decides to do about that. The `hello` handshake pins
`GHOSTTY_COMMIT`; the browser bundle must carry the same bytes. And every
`socket.write` — daemon side, client side, WebSocket side — needs the queue
described above.
