# M1 — the `ghostty-wasm` adapter

What the proposal's §7 M1 row asks: a loader over upstream's freestanding
WASM build with layout discovery from `ghostty_type_json`, then write /
resize / plainText / emitVt / effects / both encoders. The stop condition is
"the ABI cannot be marshalled reliably from `ghostty_type_json`".

This file has a section per capability. The render consumer and the two
input encoders are marked _pending_; everything else is built and measured.

The code is under [`../src/engine/`](../src/engine/): the seam in
`types.ts`, the adapter in `ghostty-wasm/`, and the vendored artifact under
[`../vendor/ghostty-vt/`](../vendor/ghostty-vt/).

## The pin

Upstream publishes the WASM only from the rolling `tip` channel: the `tip`
GitHub release and `tip.files.ghostty.org/<sha>/`. The release's
`targetCommitish` is `main`'s head, its assets were last updated at
2026-09-01T17:47:59Z, and the `release-tip.yml` workflow run at that time
has `head_sha` `3c1ef5b3…`. `tip.files.ghostty.org/3c1ef5b3…/ghostty-vt-small.wasm`
is byte-identical to the release asset (same sha256), which settles which
commit the asset was built from. The `tip` git tag itself points at a tag

## The shape of `ghostty_type_json`

A schema-1 document: `abi` (wasm32, freestanding, 4-byte pointers and
`size_t`, 16-byte max alignment, little-endian), `library_version`, and
`types`, a map of 159 entries. Six kinds:

| kind     | count | carries                                                                                                        |
| -------- | ----- | -------------------------------------------------------------------------------------------------------------- |
| `struct` | 56    | `fields`: name → `{offset, size, type, elem?, const?, nullable?, count?, tag?, arms?}`                         |
| `union`  | 5     | same as struct with every offset 0                                                                             |
| `enum`   | 71    | `underlying` (`i32`), `prefix` (`GHOSTTY_…`), `values`: un-prefixed name → number                              |
| `packed` | 1     | `GhosttyCell`: `underlying` `u64`, `bits`: name → `{lsb, width, type}`, one bit-range is itself a tagged union |
| `alias`  | 6     | `type`: a scalar (`GhosttyRow` = `u64`, `GhosttyStyleId` = `u16`, `GhosttyMode` = `u16`, …)                    |
| `opaque` | 20    | handles; size 4                                                                                                |

Field types are scalars (`u8 u16 u32 u64 i8 i32 f32 f64 bool`), `pointer`
(with `elem`), `array` (with `elem` and `count`), or another type's name. A
struct field of union type can carry `tag` (the sibling discriminant) and
`arms` (enum member name → union member, or null): `GhosttyStyleColor`,
`GhosttyPoint` and `GhosttyTerminalScrollViewport` use it. Sized structs are
recognisable by a leading `size: u32` field.

The document is enough to write every read and write the adapter does without
a hand-transcribed offset; the headers were used to learn function signatures
and semantics, never for layout. `layout.ts` parses it and `loader.ts`
marshals through it: `sizeOf`, `allocType` (zeroed, `size` field set),
`read`/`write` for scalars, enums by name, structs, arrays and tagged unions,
`decodePacked` for `GhosttyCell`, `withOpaque` for handle constructors, and
`check` which turns a `GhosttyResult` into a `GhosttyError` carrying the
enum name.

## ABI surprises, against the proposal's three

| Proposal's note                                                            | Found                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ghostty_terminal_new` accepts `0` for the allocator                       | Confirmed. Every `allocator` parameter in the API takes 0; `ghostty_free(0, ptr, len)` releases library-allocated buffers                                                                                                                                                                                                                                                        |
| `ghostty_terminal_resize` takes five arguments                             | Confirmed; the header documents `cell_width_px` and `cell_height_px`. The adapter passes 8×16. A same-size resize returns `SUCCESS` and changes nothing                                                                                                                                                                                                                          |
| By-value option structs arrive as pointers; each nested `size` must be set | The pointer half is confirmed and general: every by-value struct parameter (`GhosttyFormatterTerminalOptions`, `GhosttyWriter`, `GhosttyPoint`) is a pointer under wasm32, visible as the export's arity. The `size` half is not enforced on this build — the formatter accepts the outer, nested or all sizes left at zero. The loader sets them all anyway; the header says to |

Three more, not in the proposal:

- Out-parameters for pre-allocated handles are pointers to the handle, not the
  handle. `ghostty_render_state_get(state, ROW_ITERATOR, &iter)` and
  `ghostty_render_state_row_get(iter, CELLS, &cells)` take a slot holding the
  handle; passing the handle itself is `INVALID_VALUE`. Upstream's
  `example/c-vt-render` shows the pattern.
- 64-bit values (`GhosttyCell`, `GhosttyRow`) are i64 parameters and cross the
  boundary as `BigInt`.
- A C function pointer is an index into the exported
  `__indirect_function_table`, and the callback options of
  `ghostty_terminal_set` take that index _as_ the value argument, not a
  pointer to a slot holding it — the header's "Input type:
  GhosttyTerminalBellFn" is literal, unlike `TITLE` (`GhosttyString*`) or
  `CONTINUATION_MAX_BYTES` (`size_t*`). The type JSON describes these fields
  only as `pointer` with `elem: "function"` (in `GhosttyReader` and
  `GhosttyWriter`); the signatures come from the headers. How a JS function
  gets an index is under _effects_ below.

Memory growth behaves as `wasm.h` says: allocations can grow linear memory
(7 pages at start, 30 after one small terminal's scratch, 746 after a hundred
80×24 terminals), the old `ArrayBuffer` detaches, and re-deriving views on
identity or length change is sufficient. A test writes, forces growth, and
reads back.

## Loading, and the compiled binary

`import wasm from "…/ghostty-vt-small.wasm" with { type: "file" }` is the
form `bun build --compile` embeds: inside the binary the path is
`/$bunfs/root/ghostty-vt-small-<hash>.wasm` and `Bun.file()` reads it.
`Bun.file(import.meta.dir + "/…")` is not embedded and fails with `ENOENT`
once compiled; a plain `import "…/x.wasm"` behaves like the `file` form on
1.3.14 but is undocumented. `spikes/m1/embedded.ts` is compiled by its test
into `dist/m1/embedded` (90.9 MB) and run from an empty temporary directory
with `PATH` unset: it reports the bunfs path, 189 exports, a bold cell and the
expected text. The loader itself (`loader.ts`, `layout.ts`, `index.ts`) uses
no Bun API, so M4 can reuse it in the browser with a `fetch()` in place of
`bytes.ts`.

## Capabilities

### create

`ghostty_terminal_new(0, slot, cols, rows)`. The seam's `scrollback` is a line
count, applied through `ghostty_terminal_set(SCROLLBACK_MAX_LINES)`.
`create()` also turns on continuation tracking (`CONTINUATION_MAX_BYTES`,
64 KiB) so that a snapshot taken between two bytes of an escape sequence
still encodes; see _encodeState_ below.

libghostty has two scrollback caps and prunes whole pages when either is
crossed. The byte cap defaults to 10,000 bytes, which, page-granular, keeps
about one page whatever the line cap says: 957 rows total on an 80×24 after
5,000 lines, the "retaining 956" the proposal saw. The adapter therefore
removes the byte cap (a NULL value) so the line count governs. Retained
counts then land within a page of the limit, on either side: a limit of 200
keeps 283 rows, 2,000 keeps 1,631. `SCROLLBACK_MAX_LINES` reads back as set;
it reports `NO_VALUE` when unlimited.

Grapheme clustering (DEC mode 2027) is off by default in libghostty, so a
ZWJ sequence lands in three wide cells; with `CSI ? 2027 h` it is one cell of
five codepoints. Whether the daemon should turn it on by default
(`GHOSTTY_TERMINAL_OPT_MODE_DEFAULT`) is probably a question for M4, since it
affects what a browser renderer sees and what a re-emitted stream tells a
user's own terminal.

### write

`ghostty_terminal_vt_write(term, ptr, len)` from a staging buffer the
terminal keeps in wasm memory (64 KiB, doubled when a chunk is larger). The
call never fails.

### resize

`ghostty_terminal_resize(term, cols, rows, 8, 16)`. 200 lines of 68 columns
on an 80×24 terminal, resized to 40 columns, wrap into head-and-tail pairs;
resized to 120 they rejoin, and the viewport shows the same last line
throughout. Growing rows re-exposes scrollback as the header says.

### plainText

The formatter, `GHOSTTY_FORMATTER_FORMAT_PLAIN`, `trim` on, `unwrap` off.
Without a selection the formatter emits the whole active screen, scrollback
included (101 lines after 100 writes on a 24-row terminal), so the adapter
builds a `GhosttySelection` from two `ghostty_terminal_grid_ref` lookups at
viewport (0,0) and (cols−1, rows−1). The formatter drops trailing blank rows
and trailing whitespace; the adapter pads to exactly `rows` lines. Output
goes through `ghostty_formatter_format_alloc` and back via `ghostty_free`.

### styledCells

The render state. One `ghostty_render_state_update`, a row iterator, and per
row one `GHOSTTY_RENDER_STATE_ROW_DATA_CELLS_RAW` query that returns a
borrowed view of every packed `GhosttyCell`, decoded with the packed
descriptor from the type JSON: content tag, codepoint or background colour,
style id, wide (narrow / wide / spacer tail / spacer head). Only cells that
need more go through the per-cell handle — `row_cells_select(x)` then
`STYLE` for a non-zero style id and `GRAPHEMES_UTF8` for a multi-codepoint
grapheme. Styles come back as `GhosttyStyle`: palette or RGB colours and the
flag set; bold, italic, underline, inverse, strikethrough, 16/256/truecolor
foregrounds and a BCE background-only run are all checked. CJK and emoji
occupy a wide cell plus a zero-width tail.

plainText and styledCells are read through different APIs on purpose; the
tests assert they agree, and the differential corpus in M6 can lean on that.

### dispose

`ghostty_terminal_free` plus the render state, iterator, cells handle and
every scratch struct. Idempotent; use after dispose throws.

### emitVt

The same formatter as plainText with `emit = VT`, `trim` off, and every
`GhosttyFormatterScreenExtra` flag on: `cursor`, `style`, `hyperlink`,
`protection`, `kitty_keyboard`, `charsets`. The options struct is the one
plainText already marshals; the screen extras are six bools after the size
field of the innermost nested struct, at offset 12 of
`GhosttyFormatterTerminalExtra`, itself at offset 12 of the options. None of
the terminal-level extras (`palette`, `modes`, `scrolling_region`,
`tabstops`, `pwd`, `keyboard`) are set; the daemon in M2 will probably want
`modes` and `scrolling_region` for a TUI reattach, and they cost nothing to
add.

What the flags mean turned out narrower than their names. Each cell's own
SGR is always in the stream; `style` governs only the SGR state pending at
the cursor, `hyperlink` only a hyperlink still open at the cursor, so the
seam's `cursor` and `style` options map onto the flags directly and the
stream's shape is: `CSI 0 m`, the rows joined by `CR LF` with SGR runs and
resets, `CUP` to the cursor, then the pending SGR. It does not clear or home
the terminal it lands in; the daemon has to send `CSI 2 J CSI H` (or `3 J`)
first.

| Measured                                                                                                      | Value                                                                                    |
| ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Styled 40×12 screen (bold/italic/underline/inverse, 16/256/truecolour, CJK, emoji, a link, cursor mid-screen) | **206 bytes**; the proposal's screen gave 211                                            |
| Round trip into a fresh terminal                                                                              | plainText, styledCells and cursor identical; re-emitting from the copy is byte-identical |
| The same screen as a snapshot                                                                                 | 1,693 bytes, for scale                                                                   |

Three things do not survive re-emission, and the tests assert each so the
corpus records them:

- **Soft wrap.** 60 characters on a 40-column terminal replay as two rows
  with a hard newline. Resize both to 80: the original rejoins, the copy
  stays split. The proposal's defect, confirmed.
- **Background-only cells.** A row erased with a background colour (`SGR 42`
  then `EL`, the BCE case) comes out as an empty line; the copy's cells are
  default-background.
- **Closed hyperlinks.** A cell in a link that was closed with `OSC 8 ; ;`
  carries `hyperlink = 1` in its packed `GhosttyCell`, but the VT stream
  has no `OSC 8` for it. Only a link still open at the cursor is emitted.

The snapshot has none of the three.

`scrollback: true` emits the whole active screen, scrollback first, with
one correction: the formatter drops the viewport's trailing blank rows, so
a copy fed the raw stream ends up scrolled short by that many rows and the
formatter's viewport-relative `CUP` then lands on the wrong line. The
adapter emits without the formatter's cursor, pads with one `CR LF` per
trailing blank row, and writes its own `CUP`. A cleared viewport over
retained scrollback and a cursor mid-viewport both come out aligned, with
`TOTAL_ROWS` matching the source.

### effects

Callbacks. Each is a `GhosttyTerminalOption` set with `ghostty_terminal_set`,
takes the terminal handle as its first argument, and is invoked
synchronously inside `ghostty_terminal_vt_write`. The module imports nothing,
so a JS function has to get into the function table after instantiation.
On Bun 1.3.14:

| Route                                                                                                        | Result                                                       |
| ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| `WebAssembly.Function` (the type-reflection proposal)                                                        | Not present on JSC                                           |
| `table.grow(1)` then `table.set(idx, plainJsFunction)`                                                       | `TypeError: Argument value did not match the reference type` |
| A trampoline module that imports the JS function and exports it, then `table.set(idx, trampoline.exports.f)` | Works. `GhosttyModule.hostFunction(signature, fn)` builds it |

The trampoline is a hand-assembled binary of about forty bytes: one type,
one import `e.f`, one export `f`. It is compiled once per signature with
`new WebAssembly.Module`, which is synchronous and, in browsers, allowed on
the main thread for modules this small, so the route should carry to M4.
Table slots are never reclaimed; the adapter registers six host functions
per module the first time any terminal subscribes, and they dispatch on the
handle they are handed, so a hundred terminals cost six slots. `userdata` is
set but unused.

What each callback receives, from the headers, and what the adapter reads:

| Option                 | Signature (wasm32)               | Read                                                                                        |
| ---------------------- | -------------------------------- | ------------------------------------------------------------------------------------------- |
| `BELL`                 | `(terminal, userdata)`           | nothing                                                                                     |
| `TITLE_CHANGED`        | `(terminal, userdata)`           | `ghostty_terminal_get(TITLE)`, a borrowed `GhosttyString`; fine to read inside the callback |
| `PWD_CHANGED`          | `(terminal, userdata)`           | `ghostty_terminal_get(PWD)`; raw bytes, so `file://host/path` for OSC 7                     |
| `WRITE_PTY`            | `(terminal, userdata, ptr, len)` | copied out before returning; the bytes are borrowed                                         |
| `DESKTOP_NOTIFICATION` | `(terminal, userdata, ptr)`      | a sized struct with two `GhosttyString`s, `title` and `body`; OSC 9 gives an empty title    |
| `PROGRESS_REPORT`      | `(terminal, userdata, ptr)`      | a sized struct: `state` enum and `progress` as `i8`, −1 when omitted                        |

All six fire in the test: OSC 0 and OSC 2 titles, OSC 7 pwd, BEL, OSC 9;4
progress in `set` / `indeterminate` / `remove` states, OSC 9 and OSC 777
notifications, and `write-pty` for DSR 6 (`CSI 1;1 R`), DECRQM
(`CSI ?1;2 $y`) and DA1 (`CSI ?62;22 c`). DA1 is answered without a
`DEVICE_ATTRIBUTES` callback; that option exists to override the response.
The other callbacks in the header — `ENQUIRY`, `XTVERSION`, `SIZE`,
`COLOR_SCHEME`, `DEVICE_ATTRIBUTES`, both clipboard directions,
`UNKNOWN_SEQUENCE` — are reachable by the same route and are not wired;
`SIZE` is the one M2 will probably want, because a program asking
`CSI 18 t` gets nothing until it is.

Two things the daemon must know. A listener that throws would unwind
through libghostty's frames mid-write, so the adapter parks the first
exception and rethrows it from `write()` after the call returns; the
terminal is consistent afterwards. And with no listener registered the
terminal still consumes the sequences and answers nothing, which is what
the header says and what a headless daemon would see if it forgot to
subscribe: DSR replies are only produced when something is listening, so
`onEffect` has to be called before the child's first byte.

### encodeState / decodeState

`ghostty_snapshot_encode_alloc(term, NULL, &ptr, &len)` and the incremental
decoder over `ghostty_snapshot_decoder_new_buf`. The decoder borrows the
source bytes until FINISH, so the adapter copies them into wasm memory and
keeps them until the decode finishes or is abandoned.

| Measured, 80×24, 5,000 lines written, 2,000-line scrollback | Value                                                                         |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Rows retained                                               | 1,631 (24 active, 1,607 scrollback)                                           |
| Snapshot                                                    | **20,716 bytes**, `GHOSTSNP` magic, format version 1; 0.4–1.7 ms to encode    |
| `ready()`                                                   | 0.4–1.4 ms; **283 rows** renderable, the viewport identical to the source     |
| Pending after `ready()`                                     | **1,348 rows**, from `HISTORY_ROWS_PRIMARY` (1,607) minus what `ready()` gave |
| `next()`                                                    | 2 pages of 674 rows, `remaining` 1 then 0, 0.7–3.6 ms to FINISH               |
| After FINISH                                                | `TOTAL_ROWS` 1,631; the full-buffer plain text is identical to the source     |

The proposal's 54,655 bytes for "956 rows" was measured with libghostty's
default 10,000-byte scrollback cap; the same terminal under that cap
encodes here to 12,594 bytes for 957 rows, so the format has got tighter
since, or the proposal's screen had more in it. Either way it is a few
bytes per row.

The renderable prefix is the newest page of scrollback plus the active
area, so the two-stage split only shows once history exceeds a page: on the
40×12 case `ready()` already holds everything and `next()` returns null at
once. Timings above spread because they were taken on cold and warm JIT.

What the snapshot carries that a caller might not expect: the scrollback
caps (`SCROLLBACK_MAX_LINES` reads back as 2,000 and the byte cap as
`NO_VALUE` on the restored terminal, so it keeps pruning the way the source
did), both screens (a snapshot taken on the alternate screen restores with
the alternate active and the primary intact underneath), and the pending
SGR at the cursor.

**Continuation.** Encoding a terminal whose parser is mid-sequence is
`INVALID_VALUE` unless continuation tracking was on _before_ the unfinished
bytes were written, so `create()` sets `CONTINUATION_MAX_BYTES` to 64 KiB
(`continuationMaxBytes` overrides it; 0 disables). A snapshot taken after
`ESC [ 3` then completed with `1 m X` on both sides gives a red `X` in both;
the 20×3 case encodes to 1,092 bytes with the two bytes of continuation
inside it. The decoder is created with `RETAIN_CONTINUATION` on and the
same limit, so a restored terminal can be snapshotted mid-sequence again
after live input; the header warns that a continuation past the limit
becomes unavailable until the parser next reaches ground, and encodeState
throws until then.

**Ownership.** `ready()` hands over a caller-owned terminal and the decoder
keeps a borrowed reference for `next()`; the terminal must outlive the
decoder, not the other way round. The adapter's `GhosttyWasmDecodedState`
frees the decoder and the source copy on FINISH, on `dispose()`, or when
the terminal from `ready()` is disposed first; freeing the decoder leaves
the terminal usable with whatever history had arrived. `ready()` is
idempotent, `next()` before `ready()` is an error, and garbage bytes fail
in `ready()` with a `GhosttyError` rather than at construction, because
`decoder_new_buf` only stores the pointer. The seam's `Page` is
`{ screen, rows, remaining }` straight from `PROGRESS_SCREEN`,
`PROGRESS_ROWS` and `PROGRESS_REMAINING`; `remaining` counts pages left in
that screen's sequence only, and `next()` returning null is the one signal
that the snapshot is complete.

## Throughput

4 MiB of mixed text and escapes (SGR colours, bold, truecolor, CJK, emoji)
into a 120×40 terminal with 2,000 lines of scrollback, in 64-line chunks: 165
to 168 MiB/s on Bun 1.3.14, interpreted. The proposal's baseline of ~107
MiB/s was Node on a different corpus; nothing was tuned. Memory stayed at 2.9
MiB of linear memory after several 5,000-line terminals were created and
freed.

## Verdict on the M1 stop condition

"The ABI cannot be marshalled reliably from `ghostty_type_json`" — **not
hit**. Every offset, size, enum value and bit position the adapter uses came
from the document; the headers were read for signatures and semantics only.
The three things a reader of the document alone would not know — that
by-value structs are pointers, that handle out-parameters are pointers to
slots, and that callback options take a table index as their value — are
wasm32 C ABI and libghostty conventions rather than gaps in the layout, and
all three are in the loader's comments. The question the proposal flagged
as the hard one, callbacks into a module with no imports, closed on the
first working route: a trampoline module per signature.

What remains for M1's row are the render consumer and the two input
encoders. Nothing seen here suggests either is blocked; the encoders are 38
plain exports and the render state's `next_dirty` is already exercised
without its bookkeeping.
