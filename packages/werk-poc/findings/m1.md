# M1 — the `ghostty-wasm` adapter

What the proposal's §7 M1 row asks: a loader over upstream's freestanding
WASM build with layout discovery from `ghostty_type_json`, then write /
resize / plainText / emitVt / effects / both encoders. The stop condition is
"the ABI cannot be marshalled reliably from `ghostty_type_json`".

The work is in two halves. This file has a section per capability so the
second half appends rather than rewrites. Sections marked _pending_ are the
other half.

The code is under [`../src/engine/`](../src/engine/): the seam in
`types.ts`, the adapter in `ghostty-wasm/`, and the vendored artifact under
[`../vendor/ghostty-vt/`](../vendor/ghostty-vt/).

## The pin

Upstream publishes the WASM only from the rolling `tip` channel: the `tip`
GitHub release and `tip.files.ghostty.org/<sha>/`. The release's
`targetCommitish` is `main`'s head, its assets were last updated at
2026-09-01T17:47:59Z, and the `release-tip.yml` workflow run at that time
has `head_sha` `3c1ef5b3…`. `tip.files.ghostty.org/3c1ef5b3…/ghostty-vt-small.wasm`
is byte-identical to the release asset (same sha256), which settles which
commit the asset was built from. The `tip` git tag itself points at a tag
object, not a commit, so it is not the reference to use.

The same commit's `include/ghostty/vt.h`, `include/ghostty/vt/**/*.h` (34
headers) and `LICENSE` sit next to the artifact. `fetch.ts` refetches any
commit by sha; only the pinned one is checked in.

## The shape of `ghostty_type_json`

A schema-1 document: `abi` (wasm32, freestanding, 4-byte pointers and
`size_t`, 16-byte max alignment, little-endian), `library_version`, and
`types`, a map of 159 entries. Six kinds:

| kind     | count | carries                                                                                                        |
| -------- | ----- | -------------------------------------------------------------------------------------------------------------- |
| `struct` | 56    | `fields`: name → `{offset, size, type, elem?, const?, nullable?, count?, tag?, arms?}`                         |
| `union`  | 5     | same as struct with every offset 0                                                                             |
| `enum`   | 71    | `underlying` (`i32`), `prefix` (`GHOSTTY_…`), `values`: un-prefixed name → number                              |
| `packed` | 1     | `GhosttyCell`: `underlying` `u64`, `bits`: name → `{lsb, width, type}`, one bit-range is itself a tagged union |
| `alias`  | 6     | `type`: a scalar (`GhosttyRow` = `u64`, `GhosttyStyleId` = `u16`, `GhosttyMode` = `u16`, …)                    |
| `opaque` | 20    | handles; size 4                                                                                                |

Field types are scalars (`u8 u16 u32 u64 i8 i32 f32 f64 bool`), `pointer`
(with `elem`), `array` (with `elem` and `count`), or another type's name. A
struct field of union type can carry `tag` (the sibling discriminant) and
`arms` (enum member name → union member, or null): `GhosttyStyleColor`,
`GhosttyPoint` and `GhosttyTerminalScrollViewport` use it. Sized structs are
recognisable by a leading `size: u32` field.

The document is enough to write every read and write the adapter does without
a hand-transcribed offset; the headers were used to learn function signatures
and semantics, never for layout. `layout.ts` parses it and `loader.ts`
marshals through it: `sizeOf`, `allocType` (zeroed, `size` field set),
`read`/`write` for scalars, enums by name, structs, arrays and tagged unions,
`decodePacked` for `GhosttyCell`, `withOpaque` for handle constructors, and
`check` which turns a `GhosttyResult` into a `GhosttyError` carrying the
enum name.

## ABI surprises, against the proposal's three

| Proposal's note                                                            | Found                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ghostty_terminal_new` accepts `0` for the allocator                       | Confirmed. Every `allocator` parameter in the API takes 0; `ghostty_free(0, ptr, len)` releases library-allocated buffers                                                                                                                                                                                                                                                        |
| `ghostty_terminal_resize` takes five arguments                             | Confirmed; the header documents `cell_width_px` and `cell_height_px`. The adapter passes 8×16. A same-size resize returns `SUCCESS` and changes nothing                                                                                                                                                                                                                          |
| By-value option structs arrive as pointers; each nested `size` must be set | The pointer half is confirmed and general: every by-value struct parameter (`GhosttyFormatterTerminalOptions`, `GhosttyWriter`, `GhosttyPoint`) is a pointer under wasm32, visible as the export's arity. The `size` half is not enforced on this build — the formatter accepts the outer, nested or all sizes left at zero. The loader sets them all anyway; the header says to |

Two more, not in the proposal:

- Out-parameters for pre-allocated handles are pointers to the handle, not the
  handle. `ghostty_render_state_get(state, ROW_ITERATOR, &iter)` and
  `ghostty_render_state_row_get(iter, CELLS, &cells)` take a slot holding the
  handle; passing the handle itself is `INVALID_VALUE`. Upstream's
  `example/c-vt-render` shows the pattern.
- 64-bit values (`GhosttyCell`, `GhosttyRow`) are i64 parameters and cross the
  boundary as `BigInt`.

Memory growth behaves as `wasm.h` says: allocations can grow linear memory
(7 pages at start, 30 after one small terminal's scratch, 746 after a hundred
80×24 terminals), the old `ArrayBuffer` detaches, and re-deriving views on
identity or length change is sufficient. A test writes, forces growth, and
reads back.

## Loading, and the compiled binary

`import wasm from "…/ghostty-vt-small.wasm" with { type: "file" }` is the
form `bun build --compile` embeds: inside the binary the path is
`/$bunfs/root/ghostty-vt-small-<hash>.wasm` and `Bun.file()` reads it.
`Bun.file(import.meta.dir + "/…")` is not embedded and fails with `ENOENT`
once compiled; a plain `import "…/x.wasm"` behaves like the `file` form on
1.3.14 but is undocumented. `spikes/m1/embedded.ts` is compiled by its test
into `dist/m1/embedded` (90.9 MB) and run from an empty temporary directory
with `PATH` unset: it reports the bunfs path, 189 exports, a bold cell and the
expected text. The loader itself (`loader.ts`, `layout.ts`, `index.ts`) uses
no Bun API, so M4 can reuse it in the browser with a `fetch()` in place of
`bytes.ts`.

## Capabilities

### create

`ghostty_terminal_new(0, slot, cols, rows)`. The seam's `scrollback` is a line
count, applied through `ghostty_terminal_set(SCROLLBACK_MAX_LINES)`.

libghostty has two scrollback caps and prunes whole pages when either is
crossed. The byte cap defaults to 10,000 bytes, which, page-granular, keeps
about one page whatever the line cap says: 957 rows total on an 80×24 after
5,000 lines, the "retaining 956" the proposal saw. The adapter therefore
removes the byte cap (a NULL value) so the line count governs. Retained
counts then land within a page of the limit, on either side: a limit of 200
keeps 283 rows, 2,000 keeps 1,631. `SCROLLBACK_MAX_LINES` reads back as set;
it reports `NO_VALUE` when unlimited.

Grapheme clustering (DEC mode 2027) is off by default in libghostty, so a
ZWJ sequence lands in three wide cells; with `CSI ? 2027 h` it is one cell of
five codepoints. Whether the daemon should turn it on by default
(`GHOSTTY_TERMINAL_OPT_MODE_DEFAULT`) is probably a question for M4, since it
affects what a browser renderer sees and what a re-emitted stream tells a
user's own terminal.

### write

`ghostty_terminal_vt_write(term, ptr, len)` from a staging buffer the
terminal keeps in wasm memory (64 KiB, doubled when a chunk is larger). The
call never fails.

### resize

`ghostty_terminal_resize(term, cols, rows, 8, 16)`. 200 lines of 68 columns
on an 80×24 terminal, resized to 40 columns, wrap into head-and-tail pairs;
resized to 120 they rejoin, and the viewport shows the same last line
throughout. Growing rows re-exposes scrollback as the header says.

### plainText

The formatter, `GHOSTTY_FORMATTER_FORMAT_PLAIN`, `trim` on, `unwrap` off.
Without a selection the formatter emits the whole active screen, scrollback
included (101 lines after 100 writes on a 24-row terminal), so the adapter
builds a `GhosttySelection` from two `ghostty_terminal_grid_ref` lookups at
viewport (0,0) and (cols−1, rows−1). The formatter drops trailing blank rows
and trailing whitespace; the adapter pads to exactly `rows` lines. Output
goes through `ghostty_formatter_format_alloc` and back via `ghostty_free`.

### styledCells

The render state. One `ghostty_render_state_update`, a row iterator, and per
row one `GHOSTTY_RENDER_STATE_ROW_DATA_CELLS_RAW` query that returns a
borrowed view of every packed `GhosttyCell`, decoded with the packed
descriptor from the type JSON: content tag, codepoint or background colour,
style id, wide (narrow / wide / spacer tail / spacer head). Only cells that
need more go through the per-cell handle — `row_cells_select(x)` then
`STYLE` for a non-zero style id and `GRAPHEMES_UTF8` for a multi-codepoint
grapheme. Styles come back as `GhosttyStyle`: palette or RGB colours and the
flag set; bold, italic, underline, inverse, strikethrough, 16/256/truecolor
foregrounds and a BCE background-only run are all checked. CJK and emoji
occupy a wide cell plus a zero-width tail.

plainText and styledCells are read through different APIs on purpose; the
tests assert they agree, and the differential corpus in M6 can lean on that.

### dispose

`ghostty_terminal_free` plus the render state, iterator, cells handle and
every scratch struct. Idempotent; use after dispose throws.

### emitVt

_Pending._ `GhosttyFormatterTerminalOptions.emit = VT` with the
`GhosttyFormatterScreenExtra` flags; the options struct already marshals.

### effects

_Pending._ `ghostty_terminal_set` with the callback options
(`TITLE_CHANGED`, `PWD_CHANGED`, `BELL`, `PROGRESS_REPORT`,
`DESKTOP_NOTIFICATION`, `WRITE_PTY`). Callbacks are function pointers into
the module's `__indirect_function_table`; how a host function gets a table
index in a module with zero imports is the question this half has to answer.

### encodeState / decodeState

_Pending._ Twelve `ghostty_snapshot_*` exports.

### renderConsumer

_Pending._ The row iterator and `next_dirty` are exercised above without the
dirty bookkeeping.

### encodeKey / encodeMouse

_Pending._ 21 and 17 exports respectively.

## Throughput

4 MiB of mixed text and escapes (SGR colours, bold, truecolor, CJK, emoji)
into a 120×40 terminal with 2,000 lines of scrollback, in 64-line chunks: 165
to 168 MiB/s on Bun 1.3.14, interpreted. The proposal's baseline of ~107
MiB/s was Node on a different corpus; nothing was tuned. Memory stayed at 2.9
MiB of linear memory after several 5,000-line terminals were created and
freed.

## Verdict on the M1 stop condition, first half

"The ABI cannot be marshalled reliably from `ghostty_type_json`" — **not
hit**. Every offset, size, enum value and bit position the adapter uses came
from the document; the headers were read for signatures and semantics only.
The two things a reader of the document alone would not know — that by-value
structs are pointers, and that handle out-parameters are pointers to slots —
are wasm32 C ABI and libghostty conventions rather than gaps in the layout,
and both are now in the loader's comments. The second half has the harder
question, callbacks into a module with no imports; nothing seen here suggests
it is blocked.
